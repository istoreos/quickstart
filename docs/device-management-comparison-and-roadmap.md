## 1. 文档目的

这份文档用于长期回答四个问题：

1. Quickstart 设备管理当前拥有哪些能力；
2. 与 LuCI 设备概览集成相比还缺什么、哪里更强；
3. 下一大阶段怎样同时调整产品交互、后端模型和前端实现；
4. 每次改动后，如何基于同一组口径继续比较和验收。

产品目标不是复制 LuCI 表格，而是把 Quickstart 从“若干设备配置页面”演进为一个准确、易用的设备中心：先让用户认出设备、看懂状态，再以最短路径完成静态分配、限速和断网等操作。

## 2. 对比边界：不要把 `luci-app-oui` 当成完整设备列表

`luci-app-oui` 本身只是一个可选的本地厂商图标增强包。它提供 OUI 数据、SVG 图标、最长前缀匹配和按完整 MAC 的 OEM 覆盖，但不负责发现设备、统计流量、判断在线状态或写入静态租约。

本文所称“对照实现”是以下代码共同形成的完整 LuCI 设备概览集成：

| 组成 | 职责 | 一手源码 |
| --- | --- | --- |
| `luci-app-oui` | 本地 OUI 数据、品牌图标、OEM 覆盖、fnOS 图标规则 | `/projects/workspace-linkease-ubuntu/github-sources/luci-coolsnowwolf/applications/luci-app-oui/README.md:3-26`；`.../htdocs/luci-static/resources/oui/oui.js:10-109` |
| `luci-mod-status` 的在线主机视图 | 加载 DHCP/ARP/历史数据，按设备合并地址，呈现在线状态、流量、连接数、静态租约入口 | `/projects/workspace-linkease-ubuntu/github-sources/luci-coolsnowwolf/modules/luci-mod-status/htdocs/luci-static/resources/view/status/include/40_dhcp.js:215-462` |
| `luci-client-history` | 每 10 秒采集设备，在内存文件中保留本次开机历史 | `/projects/workspace-linkease-ubuntu/github-sources/luci-coolsnowwolf/modules/luci-mod-status/root/etc/init.d/luci-client-history:6-11`；`.../root/usr/share/ucode/luci/client_history.uc:17-49` |

## 3. 功能对比基线

状态说明：

- “有”表示当前源码存在完整可用路径；
- “部分”表示有模型或后端数据，但产品界面、身份模型或使用体验不完整；
- “无”表示当前对比范围内没有对应能力；
- 对照实现的设备行来自当前 DHCPv4、DHCPv6、已解析的 `br-lan` ARP 和本次开机历史；host hints 主要用于辅助身份、地址和名称，不应被描述为单独创建设备行的数据源。

| 能力 | Quickstart 当前状态 | 对照实现当前状态 | 结论与产品含义 |
| --- | --- | --- | --- |
| 设备发现 | `DeviceInventory` 合并 DHCPv4、ARP、NDP、odhcpd DHCPv6、LAN host hints、Wi-Fi 关联和本次开机历史 | 合并当前 DHCPv4、DHCPv6、有效 `br-lan` ARP 和本次开机历史，并用 host hints 辅助归属 | 核心覆盖已接近；Quickstart 额外输出数据源健康状态，对照实现的采集链路更成熟 |
| IPv6 | 支持 IPv6-only、多 IPv6 地址、NDP、DUID+IAID boot-local 身份；暂不写 IPv6 静态保留 | 支持 DHCPv6、多 IPv6 地址、DUID/IAID 及 IPv6 静态保留 | 读取与展示已补齐；对照实现仍领先 IPv6 静态保留 |
| 同一设备多地址聚合 | 按 MAC 聚合 IPv4/IPv6；无 MAC 租约按 DUID+IAID 去重；当前地址保持唯一 owner | 按 MAC 聚合 IPv4/IPv6；MAC 缺失时仅在地址归属唯一时辅助合并，DUID/IAID 用于未知 IPv6 租约去重 | 双方均具备稳定身份与多地址；Quickstart 明确标记 boot-local 稳定范围 |
| 在线/离线与历史 | 默认只看在线，可切换全部；本次开机保留离线身份、最后出现和历史地址 | 通过当前有效 ARP 标记在线/离线；本次开机内保留已过期记录和历史地址 | 核心能力相当；Quickstart 的默认筛选更克制 |
| 厂商/OUI | 最长前缀及随机/组播/非法 MAC 过滤已部署；列表和详情展示厂商文本，未知使用通用本地图标 | 本地数据库支持 24/28/36 位最长前缀、随机/组播/非法 MAC 过滤、未知图标回退 | Quickstart 文本覆盖广；对照实现的品牌图标/OEM 覆盖仍更强 |
| OEM/设备级品牌覆盖 | 无 | `/etc/config/oui` 可按完整 MAC 覆盖品牌；不会污染整个 OUI 前缀 | Quickstart 缺失；应作为高级能力，不能增加默认页面负担 |
| 实时上传/下载 | `DeviceTraffic` 按当前地址 owner 聚合 IPv4/IPv6，3 秒轮询，支持预热/过期/降级；隐藏页面暂停 | rpcd 每 2 秒采样、前端每 2 秒刷新，支持多地址求和及 MAC 所有权校验 | 核心能力相当；Quickstart 的数据健康和页面生命周期表达更清楚 |
| 累计流量 | 有按稳定设备身份聚合的本次服务运行累计值，地址转移重置基线；详情展示 | 有按 MAC 聚合的本次采样状态累计值，并持久到 `/tmp` 状态文件 | 双方都有；对照实现的临时状态持久化更成熟，Quickstart 重启后重新累计 |
| 连接数 | 有按设备多地址合并的 conntrack 连接数，放在详情 | 有按 MAC 的 conntrack 连接数 | 核心能力相当 |
| 设备 Web 入口 | M20 支持显式安全探测，仅限清单内 LAN 地址和 80/443/8080/8443，2 秒超时、并发 4 | 探测 80、8080、5666、443、4430、5667，IP 可跳转设备管理页；限制并发和超时 | 双方均有有界探测；Quickstart 的目标校验和 SSRF 边界更严格 |

## 4. Quickstart 的优势

Quickstart 的方向不是单纯展示更多网络字段，而是把发现与控制放在同一个产品闭环中。现有优势应被保留并深化：

1. **操作闭环更完整。** 用户可从设备列表直接进入静态分配、限速、断网和流量详情，而不必跳到多个 LuCI 页面。
2. **IPv4 策略管理更丰富。** 静态分配支持名称、MAC、可选 IP 绑定、DHCP 标签、不同网关、编辑、删除和批量删除。
3. **设备控制更强。** 单设备上下行限速、全局带宽、MAC 断网及独立规则列表构成了对照实现没有的策略能力。
4. **网络角色能力独特。** DHCP 标签、自定义设备网关和浮动网关适合 iStoreOS 的主路由/旁路由场景。
5. **连接类型更直观。** 后端已经能够根据 Wi-Fi 关联表区分 Wi-Fi 与有线设备。
6. **已有聚合骨架。** 设备列表已经在后端汇总主机名、Wi-Fi、静态分配、限速和流量，为建立统一设备模型提供了基础。
7. **厂商原始数据库覆盖广。** OpenWrt 包内 `manuf` 文件当前约 55,134 行，明显多于对照图标子集的 8,637 个前缀；优势尚未转化为可靠算法和界面体验。

## 5. 当前不足与风险

### 5.1 产品和交互不足

- 尚无 OEM 完整 MAC 品牌覆盖和品牌图标扩展；当前刻意使用原创通用形态图标与品牌文字，避免许可证和误识别风险。设备 Web 管理已提供显式、LAN-only 的安全探测。
- IPv6 地址可查看、复制和参与遥测，但 IPv6 静态保留尚未开放。
- DUID+IAID 与 MAC 没有可靠关联证据时会保留为独立 boot-local 身份，可能在“全部”中与同一物理设备的 MAC 身份并列；不能用主机名强行合并。
- 统一网络规则台账已经覆盖地址、路线、限速和断网；经典编辑器仍保留在兼容区，正式退场需等 M21 的升级/回滚验证。
- 当前视觉证据覆盖浅色主题和三个视口；深色主题、长文案语言和键盘完整走查仍应纳入正式发布验收。

### 5.2 后端正确性和可维护性不足

- 本次开机设备发现历史仍不跨系统重启；M19 的小时/日/月流量历史和配额已使用受限、节流的持久化存储跨 Quickstart 重启。
- 已完成 2400 次等价 2 小时采样模拟、容量/竞态/真机快速压力；连续 2 小时墙钟真机 soak 的结果记录在 `docs/evidence/m12/acceptance.md`。
- 目标内核拒绝 conntrack `ProtoUnspec` netlink dump，当前自动回退 `/proc/net/nf_conntrack`；后续升级内核或库时需同时回归两条采样路径。
- `DevicePolicy` 有文件级事务回滚和自动测试，但测试机没有执行真实 DHCP/防火墙/eqos 写入；在单独授权的写入验收前，不能宣称目标固件上的事务闭环已实机验证。
- `DeviceInventory`、`DeviceTraffic`、`DevicePolicy` 已形成深模块；旧接口仍在兼容窗口内，暂不删除以保证快速回退。

### 5.3 打包和发布不足

## 6. 下一大阶段：设备中心 2.0

### 6.1 阶段目标与非目标

阶段目标：

- 建立可信、稳定的设备身份与多地址模型；
- 补齐 IPv6、在线/离线、开机历史和厂商识别；
- 修正流量归属与资源上限，再增加累计流量和连接数；
- 将策略能力融入设备详情和快捷操作，同时保留独立规则台账；
- 用渐进披露控制信息密度，使普通用户无需理解 DHCP、DUID、conntrack 等术语。

本阶段非目标：

- 不把 LuCI 的每一个字段原样搬入默认列表；
- 不做永久跨重启的设备画像库；历史默认只保留在 `/tmp`，避免频繁写闪存；
- 不通过公网服务上传 MAC 查询厂商；
- 不在没有验证和回滚方案时自动修改测试机网络、DHCP、限速或浮动网关配置；
- 不为每个数据源新增一个向外暴露的浅薄接口。
- 不在完成许可证、素材来源和商标审查前复制对照实现或图标资产。

### 6.2 产品信息架构

下一阶段保留用户已经熟悉的四类能力，但调整层级：

1. **设备**：默认入口，统一展示在线和本次开机发现过的设备；承担查找、识别和快捷控制。
2. **规则**：承载“静态分配”和“限速/断网”两个次级页签，继续提供批量管理和离线规则维护。
3. **全局设置**：承载 DHCP、全局限速和浮动网关；高级能力按安装状态和开关渐进展开。

迁移时保留原有四个页签的路由兼容或可预测跳转，避免已有入口失效。若一次合并页签风险过高，可以先保持四页签视觉结构，只完成统一设备详情和跨页回跳，再在后续小版本合并为“规则”。

### 6.3 默认设备列表：少而清晰

桌面端默认只展示六组信息：

| 默认列 | 展示方式 |
| --- | --- |
| 设备 | 本地图标、用户命名/主机名、厂商小字；未知时统一通用图标 |
| 状态 | 绿色“在线”或灰色“离线”；离线时显示“最近在线”相对时间 |
| 地址 | 主 IPv4；无 IPv4 时显示主 IPv6；存在更多地址时显示“+N” |
| 连接 | Wi-Fi/有线图标；可可靠获得时再显示 SSID/接口 |
| 实时流量 | 上下行合并在一个单元格，未就绪时显示“采集中”，不显示假 `0` |
| 策略与操作 | 静态分配、限速、断网状态摘要；一个主操作和“更多”菜单 |

下面的信息进入右侧详情抽屉，不占用默认列：完整 MAC、全部 IPv4/IPv6、历史地址、DUID/IAID、累计流量、连接数、Web 管理入口、DHCP 标签、网关、规则详情、数据新鲜度和诊断信息。

交互要求：

- 默认显示在线设备；离线设备通过“在线 / 全部 / 已控制”筛选查看，并显示计数。
- 搜索覆盖用户命名、主机名、IP、MAC 和厂商；匹配结果直接高亮关键字。
- 默认排序为“在线优先，其次最近活跃”；用户可切换“实时下载、实时上传、累计流量、名称”。不为低价值字段增加排序控件。
- 行点击打开详情抽屉；“断网”属于高影响操作，必须二次确认且确认文案包含设备名称和 MAC 后四位。
- 静态分配和限速使用短表单；高级网关/标签设置折叠在“高级选项”中。
- 成功保存后就地更新并明确反馈；失败不能用空列表代替，需保留旧数据并显示可重试提示。
- 移动端使用设备卡片，只显示设备、状态、主地址、实时流量和策略摘要；其余进入详情。
- 图标全部本地化，不把 MAC 或设备信息发送到外部服务。

### 6.4 后端模块规划

后端采用深模块：让调用者通过很小、稳定的 Interface 获得完整行为，把复杂来源和归属规则留在模块内部。深度带来两类收益：前端和其他调用者获得更高 Leverage，设备发现及归属逻辑集中后获得更好的 Locality。

#### A. `DeviceInventory` Module

建议外部 Interface 只暴露类似下面的能力：

```go
type DeviceInventory interface {
    Snapshot(ctx context.Context, options SnapshotOptions) (DeviceSnapshot, error)
}
```

`DeviceSnapshot` 返回稳定的设备语义：`deviceId`、显示名、在线状态、最近出现时间、当前/历史地址、厂商、连接类型、能力和数据健康状态。调用者不需要知道设备来自 ARP、DHCP 还是 host hints。

Implementation 内部可以有以下私有 Adapter 和内部 seam：

- DHCPv4 Adapter
- DHCPv6 Adapter
- ARP/NDP Adapter
- host hints Adapter
- Wi-Fi 关联 Adapter
- boot history Adapter
- OUI/OEM Adapter

身份规则按可靠性排序：规范化的全局 MAC；可唯一归属到 MAC 的地址；无法归属的 IPv6 设备使用 DUID+IAID 形成 boot-local 身份。主机名绝不能作为合并设备的唯一依据。地址必须区分 current/historical，且 IP 所有权变化后不得把旧地址或名字错误继承给新设备。

不要把上述 Adapter 逐个暴露到外部 Interface。生产和测试的差异通过内部 seam 注入；只有真实存在生产与测试两个 Adapter 的 seam 才值得保留。

#### B. `DeviceTraffic` Module

建议外部 Interface 聚焦设备级遥测，而不是 conntrack 记录：

```go
type DeviceTraffic interface {
    Snapshot(ctx context.Context, identities []DeviceIdentity) (TrafficSnapshot, error)
}
```

Implementation 负责：

- 只接收并统计当前 LAN 前缀/接口中的 IPv4 和 IPv6；
- 根据 `DeviceInventory` 提供的稳定 identity 和当前地址所有权，把速率、累计和连接数归属到设备；
- IP 所有权变化时重置该地址基线，防止串量；
- 设置 host、flow、请求地址和历史窗口上限，并对空闲项淘汰；
- 返回 `warming_up`、`partial`、`stale` 等可解释状态；
- conntrack Adapter 位于模块内部 seam，未来替换为 rpcd/ubus 或内核实现时，外部 Interface 不变。

第一步必须先修 `isLanIP()` 和容量/淘汰，再开放累计流量及连接数 UI。不要在不可信的采样基础上增加更多展示。

#### C. `DevicePolicy` Module

策略写入保持独立，避免发现失败或遥测失败影响配置能力。建议它围绕稳定设备身份提供少量高价值操作：

- `Get(deviceId)`：读取静态分配、网关标签、限速和断网的合并策略；
- `Apply(deviceId, change)`：校验并原子应用策略变化；
- `ListRules(kind)`：支持独立规则台账和离线规则维护。

Implementation 内部再适配 UCI、`eqos`、防火墙和 `floatip`。前端只看到“静态地址、网关策略、限速、联网权限”等产品概念，不能看到 UCI section 序号或命令拼接细节。

`DevicePolicy` 应明确能力探测和错误模式，例如 `dependency_not_installed`、`conflict`、`validation_failed`、`apply_failed`。高影响写入先生成计划并校验，再应用；需要保留幂等与可回滚路径。

#### D. Interface 与测试纪律

- 以 `DeviceInventory.Snapshot`、`DeviceTraffic.Snapshot` 和 `DevicePolicy` 的外部 Interface 作为主要测试面。
- 测试可通过内部 Adapter 注入 DHCP/ARP/NDP/conntrack 样本，但断言观察到的设备与策略结果，而不是内部 map 或调用层数。
- 新的深模块 Interface 测试建立后，删除被替代的浅层 reader 透传测试；不要在旧层和新层重复堆测试。
- 契约测试覆盖：同 MAC 多地址、IPv6-only、DUID/IAID、IP 复用、随机 MAC、历史淘汰、数据源部分失败、流量预热、容量上限和规则冲突。
- 前端类型由稳定响应契约生成或集中维护，不直接绑定 ARP flags、DHCP lease 原始字段或 conntrack tuple。

### 6.5 对外响应契约

建议新增版本化设备快照响应，保留旧接口兼容窗口。核心字段示意：

```json
{
  "deviceId": "mac:00:11:22:33:44:55",
  "displayName": "客厅电视",
  "nameSource": "user",
  "online": true,
  "lastSeenAt": "2026-09-23T12:00:00Z",
  "addresses": {
    "current": [{ "family": 4, "address": "192.168.9.20", "primary": true }],
    "historical": []
  },
  "mac": "00:11:22:33:44:55",
  "vendor": { "name": "Example", "icon": "example" },
  "connection": { "kind": "wifi" },
  "traffic": {
    "state": "ready",
    "uploadBps": 1000,
    "downloadBps": 2000,
    "totalBytes": 3000,
    "connections": 4
  },
  "policy": {
    "staticLease": true,
    "speedLimited": false,
    "networkAccess": true
  },
  "capabilities": { "reserveIPv6": true, "webOpen": false }
}
```

字段规则：

- `deviceId` 是稳定引用，不以当前 IP 作为主键；前端不得自行推导身份。
- 速率未预热或部分数据缺失时使用显式状态，不能用 `0` 混淆“无流量”和“未知”。
- `addresses.current` 与 `historical` 明确分离；默认 UI 只展示主地址。
- `capabilities` 由后端根据软件包、数据完整性和权限给出，前端不重复猜测环境。
- 旧 `/lanctrl/...` 接口在兼容期继续工作，所有新页面迁移完成并经过设备验收后再删除。

### 6.6 前端实施规划

前端按以下顺序演进：

1. 在现有四个页面统一加载、空、错误、依赖缺失和保存反馈；沿用本地通用设备图标与现有视觉语言。
2. 围绕新设备快照建立领域类型和单一 store/composable，移除 `any` 扩散以及列表、搜索结果、轮询结果的多份可变数组。
3. 重做默认设备行和移动端卡片，增加筛选、搜索、高亮、有限排序和仅含基础身份信息的详情抽屉。
4. 在既有地址展示模型中加入 IPv6 与多地址，不增加默认列；完整地址只在详情中展示。
5. 接入设备级遥测；轮询只刷新 telemetry 子状态，页面隐藏时暂停，失败退避并保留最后一次成功数据。
6. 将静态分配、限速、断网改为从详情抽屉和快捷操作复用的同一套表单；规则页继续用于批量及离线规则。
7. 国际化、键盘焦点、非颜色状态提示和危险操作确认不是最终补丁，而是对应里程碑的完成条件。

### 6.7 分阶段交付原则

设备中心 2.0 不采用一次性大改。交付顺序必须遵循“先把已有功能做清楚，再增加数据；先建立稳定身份，再接入复杂遥测和策略”的原则：

1. 每个里程碑只解决一个主要用户问题，并能独立部署、验收和回退；
2. 新接口先与旧 `/lanctrl/...` 接口并行，前端切换稳定后再讨论移除旧接口；
3. 在身份模型稳定前，不增加累计流量、连接数或复杂策略归属；
4. 在依赖能力不可用时显示“功能未安装/不可用”，不得显示空白、无限加载或笼统“系统错误”；
5. 默认页面始终保持六组以内的信息密度，复杂信息进入详情抽屉；
6. 每个里程碑都必须在桌面和移动端检查视觉质量，不以“接口已经可用”代替产品完成。

### 6.8 里程碑总览：从简单到复杂

| 里程碑 | 主要用户问题 | 用户可见结果 | 复杂度 | 前置条件 |
| --- | --- | --- | --- | --- |
| M0. 安全基线 | 现有列表错误不可见、流量边界不可靠 | 错误可重试、旧数据保留、LAN 流量过滤、无外部设备图片 | 已完成 | 无 |
| M1. 现有体验统一 | 页面状态和可选依赖表达混乱 | 四个现有页面拥有一致、清楚、好看的加载/空/错误/不可用状态 | 已完成 | M0 |
| M2. 可信 IPv4 清单 | 同一设备来源分散，无法判断在线和最近出现 | 新后端快照可按 MAC 聚合 DHCPv4、ARP、Wi-Fi 与本次开机历史 | 已完成 | M1 |
| M3. 简洁新设备列表 | 当前列表信息层级弱，移动端和查找体验不足 | 新默认设备行、筛选、搜索、高亮、有限排序和基础详情抽屉 | 已完成 | M2 |
| M4. IPv6 与多地址 | IPv6-only 设备不可见，一台设备多个地址无法表达 | IPv4/IPv6 聚合为一台设备，主地址清楚，完整地址进入详情 | 已完成 | M2、M3 |
| M5. 可信设备遥测 | 速率按 IP 归属，状态和数据新鲜度不明确 | 按设备显示速率、累计流量、连接数及预热/过期状态 | 已完成 | M4 |
| M6. 策略融合 | 静态分配、限速、断网分散且依赖错误不清楚 | 在详情内用统一短表单完成常用控制，规则台账继续处理批量和离线规则 | 已完成 | M3、M5 |

M1～M6 共同组成下一大阶段。OEM 覆盖、设备 Web 入口探测、品牌图标扩展和永久历史不进入本阶段承诺，统一放入阶段后增强池，避免核心体验被低频功能拖慢。

### 6.9 M1：现有体验统一

**目标：** 不改变当前四个一级页签和数据模型，先让用户始终知道页面正在做什么、是否成功、为什么不可用。

前端交付：

- 统一设备、静态分配、限速设备和全局设置的加载骨架、空状态、错误状态、重试按钮和保存反馈；
- 统一表格间距、状态标签、按钮层级、危险操作颜色和弹窗结构，优先复用现有设计语言，不引入另一套视觉框架；
- `eqos`、`floatip` 等依赖缺失时显示解释卡片和安装提示，隐藏不能工作的开关或表单；
- 保存期间只锁定当前表单或当前行，不冻结整个页面；成功就地更新，失败保留用户输入；
- 桌面端保持表格，移动端允许表格内部滚动，但页面本身不得横向溢出。

后端交付：

- 提供统一的只读 capability 信息，至少区分 `available`、`not_installed`、`disabled` 和 `error`；
- 保持现有配置写接口和设备响应兼容，不在本里程碑改设备身份。

明确验收目标：

- 四个页面分别通过“加载中、成功有数据、成功无数据、请求失败、依赖未安装”五类状态检查；
- 在 1440×900、1024×768 和 390×844 三种视口下无控件遮挡、文字截断导致的误解或页面级横向滚动；
- 普通操作只有一个主按钮；删除、断网等高影响操作有明确对象和二次确认；
- 测试机未安装 `eqos`/`floatip` 时不再显示笼统 `-1000` 错误；
- 不修改测试机网络、DHCP、防火墙和策略配置也可以完成全部只读验收。

**不做：** 新设备身份、IPv6、新列表结构、累计流量或页签合并。

### 6.10 M2：可信 IPv4 设备清单

**目标：** 先在 IPv4 范围内建立稳定且可解释的设备快照，为新 UI 提供可靠基础。

后端交付：

- 实现 `DeviceInventory.Snapshot` 第一版，内部合并 DHCPv4、有效 ARP、host hints 和 Wi-Fi 关联；
- 有全局 MAC 时以规范化 MAC 作为 `deviceId`，主机名只用于显示，不能参与设备合并；
- 在 `/tmp` 保存本次开机历史，输出 `online`、`lastSeenAt`、当前地址和历史地址；重启后允许历史清空；
- 输出数据源健康信息；某个增强来源失败时返回 `partial`，而不是把全部设备变成空列表；
- 新增版本化只读接口，旧接口继续工作；新接口先由测试和开发开关使用。

明确验收目标：

- 同一 MAC 同时出现在 DHCPv4、ARP 和 Wi-Fi 来源时只生成一台设备；
- ARP 消失后设备变为离线并保留在本次开机历史中，重新出现后恢复同一 `deviceId`；
- IPv4 被另一 MAC 使用时，旧名称、历史和流量基线不继承给新设备；
- 任一非核心数据源失败时仍返回可用设备和明确的 `partial/reason`；
- 契约样本至少覆盖重复来源、离线/上线、IP 复用、随机 MAC、未知厂商和容量淘汰；
- 在测试机上新旧接口并行运行，旧设备页面无功能回归。

**不做：** IPv6、累计流量、连接数、策略写入和新页面切换。

### 6.11 M3：简洁新设备列表

**目标：** 把 M2 的可靠数据转化为明显更易读的设备首页，但不在默认列表堆满技术字段。

前端交付：

- 桌面端默认展示“设备、状态、地址、连接、实时流量占位、策略与操作”六组信息；移动端卡片只展示设备、状态、主地址、流量占位和策略摘要；
- 默认筛选为“在线”，提供“全部”和“已控制”筛选及数量；
- 搜索覆盖用户命名、主机名、IPv4、MAC 和厂商，并高亮匹配部分；
- 只提供“最近活跃”和“名称”两种可靠排序；流量排序等到 M5 再开放；
- 点击设备行打开基础详情抽屉，展示完整 MAC、当前/历史 IPv4、连接方式、厂商文本、最后出现时间和数据健康信息；
- 保留现有静态分配、限速和设置页面入口，不在本里程碑合并导航。

明确验收目标：

- 用户进入页面后无需打开详情即可回答“这是谁、是否在线、当前地址是什么”；
- 从列表找到指定名称/IP/MAC 的设备不超过一次搜索和一次点击；
- 默认桌面列表不超过六组信息，390 px 宽度下使用卡片且页面无横向滚动；
- 设备每次刷新保持稳定 key，不因轮询整表闪烁、丢失展开状态或跳回顶部；
- 19 台现有测试设备均可展示；未知名称、未知厂商和超长 IPv6 预留文本不会破坏布局；
- 新旧列表可通过单一功能开关切换，出现回归时无需回滚后端即可恢复旧列表。

视觉验收必须留存 1440×900、1024×768、390×844 三组截图，覆盖正常、空、错误、离线和详情抽屉状态。颜色不得是状态的唯一表达方式，键盘焦点必须可见。

**不做：** 品牌 logo 扩展、IPv6、多地址编辑、累计流量、连接数或策略表单重写。

### 6.12 M4：IPv6 与多地址聚合

**目标：** 在不增加默认列表复杂度的前提下，让 IPv6-only 和同设备多地址场景正确可见。

后端交付：

- 增加 DHCPv6、NDP 和可用 host hints 数据源；
- 全局 MAC 仍是首选身份；无 MAC 的 IPv6 租约使用 DUID+IAID 形成 boot-local `deviceId`；
- 明确 current/historical 地址所有权与主地址选择规则，地址转移后不得串设备；
- 同一设备的 IPv4、IPv6 和临时 IPv6 聚合到同一个 snapshot。

前端交付：

- 默认地址列只显示主地址和“+N”，全部地址放在详情抽屉；
- IPv6-only 设备使用与 IPv4 设备相同的卡片和操作层级，不另建专用页面；
- 长 IPv6 地址支持复制，视觉上截断但不丢失完整值。

明确验收目标：

- IPv6-only 设备可见；同 MAC 的多个 IPv4/IPv6 只显示一行；
- 无 MAC 但相同 DUID+IAID 的租约不会重复，且明确标记其身份只在本次开机稳定；
- 地址由设备 A 转移到设备 B 后，历史归属和后续遥测不会串联；
- 默认列表仍保持六组以内，390 px 卡片不直接展开完整 IPv6 列表；
- IPv4-only 固件或无 DHCPv6 数据时页面正常降级，不显示错误占位。

**不做：** IPv6 静态保留写入；该能力进入 M6，且只有后端能力验证通过时才开放。

### 6.13 M5：可信设备遥测

**目标：** 把当前按 IP 的速率采样升级为按稳定设备身份归属，并清楚表达数据是否可用。

后端交付：

- 实现 `DeviceTraffic.Snapshot`，按 `DeviceInventory` 的当前地址所有权聚合 IPv4/IPv6；
- 提供上传/下载速率、本次开机累计流量和连接数；
- 输出 `warming_up`、`ready`、`stale`、`partial` 状态和采样时间；
- IP 所有权变化时重置该地址基线；继续执行 2048 host 上限和 10 分钟空闲淘汰。

前端交付：

- 列表仅更新 telemetry 子状态，不重建设备行；预热显示“采集中”，未知不伪装成 `0 B/s`；
- 页面不可见后 10 秒内暂停轮询，重新可见时恢复；连续失败采用退避并保留最后成功值；
- 累计流量、连接数和短时图表放入详情抽屉；列表只保留合并后的实时上下行。

明确验收目标：

- 测试机管理网段和公网对端永远不会作为 LAN 设备进入结果；
- 同设备多地址的流量只计算一次，IP 复用后不继承旧基线；
- 2 小时、约 20 台设备的持续轮询中，host cache 不超过 2048，预热后的 RSS 增长不超过 10 MB；
- 正常负载下设备快照 API 的 p95 响应时间不超过 500 ms；
- 隐藏页面后网络请求停止，恢复后不会出现瞬时重复定时器；
- conntrack 或某一地址来源失败时，设备清单仍可使用并显示遥测降级状态。

**不做：** 永久流量账单、跨重启累计或互联网云端统计。

### 6.14 M6：策略融合与信息架构收口

**目标：** 让用户围绕一台设备完成静态分配、限速和断网，同时保留适合批量管理的规则台账。

后端交付：

- 提供 `DevicePolicy.Get/Apply/ListRules`，把 UCI、`eqos`、防火墙和 `floatip` 细节封装在模块内部；
- 统一返回 `dependency_not_installed`、`conflict`、`validation_failed` 和 `apply_failed`；
- 高影响变更先校验目标和冲突，写入需要幂等，失败不得留下半应用状态；
- IPv6 静态保留只有在目标固件和回滚路径通过验证后才作为 capability 开放。

前端交付：

- 详情抽屉提供静态地址、限速和联网权限三个短表单；网关、DHCP 标签等低频字段折叠在“高级选项”；
- 行内只保留一个最常用主操作，其余进入“更多”，避免操作列变成按钮墙；
- “静态分配”和“限速设备”继续保留规则台账能力，服务于批量删除、离线规则和冲突处理；
- 只有在用户任务验证不退步后，才把两个规则页合并为“规则”二级页签；原路由保留兼容跳转。

明确验收目标：

- 从打开设备详情到完成静态分配、设置限速或断网，每项不超过 3 个主要交互步骤；
- 危险确认必须展示设备名称及 MAC 后四位，取消操作不产生请求；
- 保存失败保留表单内容和旧生效状态，成功后列表、详情和规则台账一致；
- 未安装依赖时相应能力不可操作并给出明确原因，其他设备信息仍可浏览；
- 写入测试覆盖成功、冲突、依赖缺失、中途失败、重复提交和回滚；
- 所有测试机网络/DHCP/防火墙写入必须单独列明目标、备份和回滚，并在显式授权后执行。

**不做：** OEM 品牌覆盖、Web 端口探测、永久画像和复杂自动化策略。

### 6.15 UI 与交互硬性质量门

以下标准适用于每个有前端变化的里程碑，不满足时不得标记为完成：

- **信息密度：** 默认桌面列表最多六组信息；移动卡片最多五组摘要；诊断字段只进详情；
- **操作层级：** 一个区域最多一个主按钮；低频操作进入“更多”或“高级选项”；
- **状态完整：** 加载、空、错误、部分成功、依赖缺失和无权限都有独立文案与下一步；
- **视觉一致：** 使用项目现有颜色、圆角、字号和间距 token；不为设备中心单独造一套视觉风格；
- **响应式：** 1440、1024、390 px 三档均可完成核心任务，页面级不横向滚动；
- **可访问性：** 状态不只依赖颜色；键盘焦点可见；图标按钮有文字标签或可访问名称；
- **稳定刷新：** 轮询不让表格闪烁、滚动位置跳动、抽屉关闭或用户输入丢失；
- **文案：** 默认使用“设备、地址、在线、限速、断网”等用户语言；ARP、DUID、conntrack 只出现在诊断信息中。

### 6.16 阶段完成定义

只有同时满足以下条件，设备中心 2.0 才算完成：

1. 用户能在一行/一卡片内识别设备、状态、主地址、连接和当前策略；
2. IPv4、IPv6-only、同设备多地址、离线/上线和 IP 复用均有自动契约测试；
3. 用户可在详情内查看遥测，并在不超过 3 个主要步骤内完成常用策略；
4. 未安装可选依赖、数据源部分失败和采样预热均有可理解的界面状态；
5. 桌面与移动端的核心任务、2 小时资源验收及文件级回滚通过；
6. 新接口稳定运行一个发布窗口，旧接口才可进入弃用计划。

当前进度：M0～M10 的代码、自动验证和测试机文件级灰度部署已经完成。设备中心 2.0 的统一状态、IPv4/IPv6 稳定身份、简洁响应式列表、按设备遥测、详情内策略融合、可解释设备分类和人工修正均已达成验收；经典列表与规则台账继续保留。已经形成 `0.14.0-r2` 的预构建后端 tarball、LuCI 安装树和 OpenWrt feed 配方候选，但尚未在 OpenWrt SDK 中产出或对外上传 `.ipk`，因此不能标记为正式对外发布。

M0/M1 期间还必须完成许可证与商标审查：明确算法是独立实现还是独立 GPL 包集成，建立允许使用的 OUI 数据和图标资产清单，并把许可证/NOTICE 随发布物验证纳入验收。该审查完成前，只能使用 Quickstart 自有或已确认兼容的通用占位图标和厂商文本。

### 6.17 下一阶段：设备识别与品牌呈现

本阶段承接 M1～M6，不再增加设备列表列数，而是在现有设备身份区域内解决三个问题：未知设备的图标语义错误、原始厂商名称不易阅读、自动判断无法解释或纠正。

统一使用以下领域语义：

- **厂商（Manufacturer）**：OUI 等数据源返回的原始组织名称，例如 `ASUSTek COMPUTER INC.`；它可能是 OEM、组件或注册主体，不必然等于消费品牌；
- **品牌（Brand）**：经审核后用于界面显示的简短名称，例如 `ASUS`；品牌使用中性文字，不使用官方 logo、品牌字体或品牌专属配色；
- **设备类别（Device Category）**：电脑、手机、电视、网络设备等通用产品形态，只决定图标和类别文字，不声称精确型号；
- **设备分类（Device Classification）**：品牌、设备类别、识别来源和可信度的组合；它不是设备身份，也不得参与设备合并；
- **人工分类（Manual Classification）**：用户明确选择的设备类别，优先于自动识别，直到用户恢复自动判断。

分类优先级固定为：人工修正 → 明确型号 → 主机名/用户名称特征 → 经审核的厂商默认类别 → 通用电脑回退。网络设备图标只能由人工修正或明确的路由器、AP、Mesh、网关、交换机证据触发；单独厂商名称不得触发路由器图标。

设备名称展示规则固定为：已有用户名称或可信主机名时保留该名称；无名称但有品牌和类别时显示“品牌 + 类别”；只有品牌时显示“品牌 + 设备”；两者都没有时显示“未命名设备”。原始厂商文本进入详情，列表只显示短品牌和类别，最多两个辅助标签。

### 6.18 M7：纠正未知设备语义并突出品牌

**目标：** 在不改后端契约的前提下先修复最明显的误导，让未知设备和 `ASUSTek COMPUTER INC.` 在当前页面符合用户直觉。

任务树：

1. **回退图标**
   - 未识别设备改用通用 PC/终端形态；
   - 删除未知设备对路由器图形的依赖；
   - 图标加载失败时也回退通用 PC，不显示破图。
2. **品牌展示适配器**
   - 建立小型、可测试的短名称映射，首批至少包含 `ASUSTek COMPUTER INC.` → `ASUS`；
   - 未审核厂商保留原始厂商文本，不擅自创造品牌；
   - 随机 MAC 或无厂商信息不显示虚假品牌。
3. **列表身份层级**
   - 有名称时主标题保持原名称，第二行显示“品牌 · 类别”；
   - 无名称且可判断 ASUS 电脑时主标题显示“ASUS 电脑”；
   - 无名称、无可靠信息时显示“未命名设备”和“类型待确认”；
   - 品牌与类别使用中性文字标签，不使用厂商 logo、字体或专属配色。
4. **网络设备守门规则**
   - 只有明确出现 router、gateway、AP、mesh、交换机等证据时使用网络设备图标；
   - `ASUSTek COMPUTER INC.` 单独出现时默认通用 PC；
   - 现有 12 类场景图标继续复用，不增加列表列数。

明确验收标准：

- 无名称、无厂商的 fixture 显示“未命名设备”、通用 PC 图标和“类型待确认”；
- `manufacturer=ASUSTek COMPUTER INC.` 且无其他特征时显示“ASUS 电脑”和通用 PC 图标；
- `ASUS RT-AX88U` 或名称含 router 的 fixture 显示网络设备图标；单独 ASUS 厂商不得显示路由器；
- 已命名设备的主标题不被品牌覆盖，品牌和类别在第二行可见；
- 图标 404 fixture 能回退通用 PC，页面无破图标记；
- 桌面、1024px 和 390px 三档下身份区域不截断关键品牌、不新增页面级横向滚动；
- 自动测试至少覆盖上述五类规则，浏览器截图覆盖未知、ASUS 电脑、ASUS 路由器和有名称设备；
- 本里程碑不修改设备身份、网络、DHCP、防火墙或策略配置。

**退出条件：** 所有验收通过后可文件级灰度部署。M7 的前端推断是兼容适配器，M8 完成时必须替换而不是叠加第二套长期规则。

### 6.19 M8：统一设备分类模块与可解释契约

**目标：** 建立 `DeviceClassifier.Classify` 深模块，让分类规则只存在于后端，前端通过一个稳定接口获得品牌、类别、来源和可信度。

任务树：

1. **分类模块**
   - 输入设备名称、主机名、原始厂商、型号线索和身份范围；
   - 输出 `brand`、`manufacturer`、`category`、`source`、`confidence`；
   - 分类结果只影响呈现，不参与 `deviceId`、地址 owner、在线状态或策略关联。
2. **规则优先级**
   - 实现型号、主机名、厂商默认和通用 PC 回退的固定优先级；
   - 对冲突规则采用最具体证据优先，例如 Nintendo Switch 优先游戏设备，普通 network switch 优先网络设备；
   - ASUS 路由型号优先网络设备，只有 ASUSTek 厂商时默认电脑。
3. **品牌注册表**
   - 保存原始厂商到短品牌的显式审核映射；
   - 支持同一品牌的多个厂商拼写；
   - 对 Intel、Realtek 等可能只代表网卡或组件的厂商不得自动声称整机品牌，除非有额外型号证据。
4. **Inventory 契约**
   - `DeviceInventory.Snapshot` 为每台设备返回完整 `classification`；
   - 旧消费者忽略新字段即可继续工作；缺失分类时前端安全回退通用 PC；
   - 前端删除 M7 的自动分类实现，只保留展示和旧后端兼容适配器。
5. **可解释详情**
   - 详情展示短品牌、设备类别、原始厂商、识别依据和定性可信度；
   - 列表不显示可信度或技术来源，避免增加视觉噪声。

明确验收标准：

- 所有设备快照均包含合法 `category/source/confidence`，品牌允许为空但厂商原文不得被覆盖；
- 相同输入在重复调用和进程重启后产生相同分类；规则顺序变化不得改变明确优先级；
- 契约测试覆盖无信息、ASUSTek 默认电脑、ASUS 路由型号、Nintendo Switch、普通交换机、摄像头、NAS、打印机、穿戴设备、随机 MAC 和组件厂商；
- 分类不能改变现有 `deviceId`、当前地址、在线数量、遥测归属或策略读取结果；
- 前端列表、移动卡片和抽屉只消费同一 `classification`，不存在三套独立判断；
- M7 的临时分类规则被删除或仅保留为旧接口兼容适配器，并有旧后端响应测试；
- 测试机新旧接口并行只读验证通过，不产生任何配置写入。

**退出条件：** `DeviceClassifier.Classify` 成为分类规则的唯一测试 seam；测试通过该接口断言可观察结果，不依赖内部正则或注册表结构。

### 6.20 M9：用户修正与持久化

**目标：** 当自动分类不符合家庭实际用途时，用户可以在详情中用一个简单操作修正设备类别，并随时恢复自动判断。

任务树：

1. **人工分类存储**
   - 以持久 Device Identity 保存类别覆盖，不以 IP 或设备名称作为键；
   - boot-local 身份只允许本次开机覆盖，并明确提示不会永久保存；
   - 存储有容量上限、原子写入和损坏降级，不影响设备清单读取。
2. **分类接口**
   - 提供读取、设置类别、恢复自动判断三个动作；
   - 校验类别枚举和目标身份，重复提交保持幂等；
   - 失败返回明确错误，不留下半写状态。
3. **详情交互**
   - 在详情身份区提供“修改设备类型”，使用单选图标网格或短列表；
   - 保存只有一个主按钮，成功后就地更新列表、移动卡片和抽屉；
   - 已人工修正时显示“手动设置”，并提供次要的“恢复自动判断”。
4. **优先级与重识别**
   - 人工类别始终覆盖自动类别；品牌仍来自可信证据，不因选择类别被伪造；
   - 恢复自动后立即重新运行当前分类规则；
   - 厂商或主机名变化不会悄悄覆盖人工选择。

明确验收标准：

- 把自动识别为电脑的持久设备改成电视后，刷新页面和重启 quickstart 仍显示电视；
- 恢复自动判断后回到分类模块结果，人工记录被删除而不是保留隐藏状态；
- 重复设置同一类别不会产生重复记录或额外写入；
- 非法类别、未知 Device Identity、存储写入失败和损坏存储都有确定错误及安全回退；
- boot-local 设备明确显示“仅本次开机”，路由器重启后不会错误套用旧覆盖；
- 用户从打开详情到保存类型不超过 3 个主要交互步骤，取消不发送写请求；
- 操作只修改分类覆盖存储，DHCP、网络、防火墙、限速和设备策略配置哈希保持不变；
- 并发和回滚测试通过，浏览器自动化覆盖设置、取消、恢复自动和移动端操作。

**退出条件：** 人工修正可以可靠覆盖和撤销自动结果，且分类写入与 Device Policy 完全隔离。
