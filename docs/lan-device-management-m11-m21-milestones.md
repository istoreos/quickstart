## 1. 总目标与实施顺序

M11～M20 当时计划把现有四个分散页面收敛为三块并列区域，同时完整保留静态地址、限速、断网、DHCP 网关、浮动网关、离线规则和批量维护能力；该目标结构现已由 M21 基线取代。

实施顺序固定为：

```text
输入与写入安全
  → 性能与容量底座
  → 独立设备资料
  → Gateway Profile
  → 设备上网路线
  → 浮动网关产品化
  → 统一规则台账
  → 分组与定时策略
  → 历史、配额与洞察
  → IPv6、审计与高级集成
  → 迁移、发布与旧入口退场
```

不能跳过 M11/M12 直接增加历史或规则：当前 DHCP Hostname 写入缺少后端权威校验，设备遥测仍存在重复清单采集、全量 conntrack 分配和状态增长等需要先量化、约束的问题。

### 1.1 后续执行协议

进入实施后，每个里程碑都按同一流程执行：

1. 开始前输出该里程碑的最终任务树、验收标准、写入范围和回滚点；
2. 完成前后端、迁移、测试、打包与必要的测试机验收；
3. 对功能、视觉、性能、安全和兼容性自检；
4. 未达标时最多优化 3 次，并记录每次失败证据和改变；
5. 达标后自动进入下一里程碑；只有连续 3 次仍失败、出现新的产品语义选择或需要扩大外部写入授权时暂停。

## 2. 所有里程碑共同质量门

每个里程碑完成时都必须满足：

- 自动测试、Go race 定向测试、前端类型检查、生产构建、OpenWrt 包契约和 `git diff --check` 通过；
- 新 Interface 有成功、空、错误、容量、重复提交和降级契约测试；
- 1440×900、1024×768、390×844，浅色/深色、中英文、键盘操作无阻断；
- 可选插件失败不影响 Device Inventory 和 Device Profile；
- 高影响写入遵守 plan → validate → snapshot → apply → verify → rollback；
- 配置已保存与实际已生效分开表达；
- 不上传 MAC、设备名称、DNS 或流量数据；
- 不引入来源或许可证不清的品牌 Logo；
- 测试机写入前记录网络、DHCP、防火墙、eqos、floatip 哈希和回滚命令；
- 测试环境固定为 `root@192.168.9.215`，认证信息不写入仓库；任何会改变网络连通性的验收单独执行并确认回滚可用。

### 2.1 持续性能门

从 M12 开始，每个里程碑都重复执行：

- 页面关闭或不可见后 10 秒内停止前端遥测请求；后端无消费者 30 秒后停止 conntrack 采样并释放连接；
- 20 台真实设备连续 2 小时，Quickstart RSS 相对预热后增长不超过 10 MiB；
- 256 台设备、20,000 条合成 conntrack flow 的压力样本中，设备清单与流量快照均在规定超时内返回，不发生 OOM；
- 100,000 次设备地址/随机 MAC churn 后，host、address、totals、history、override 和事件状态全部保持在明确上限内；
- `DeviceInventory` 上限 2048、流量地址状态上限 2048；新增缓存必须声明上限、TTL、淘汰算法和降级状态；
- 默认设备页面活跃时，昂贵 Inventory 采集不得被 3 秒遥测轮询重复触发；
- 历史文件只在内容变化后节流写入，不得每次遥测请求完整重写；
- 所有性能验收同时记录 `go test -benchmem` 的 `ns/op`、`B/op`、`allocs/op` 和真机 CPU/RSS，不只记录响应时间。

### 2.2 当前统计实现的性能结论

现有实现已经有一组值得保留的防线：

- conntrack 默认 3 秒采样，30 秒没有请求后停止并关闭连接；
- 浏览器隐藏时暂停遥测请求，失败会退避；
- LAN host cache 有 2048 上限和 10 分钟 TTL，每个 host 只保留 12 个速率点；
- DeviceTraffic 地址 owner 状态有 2048 上限和 10 分钟 TTL；
- Inventory 本次开机历史有 2048 上限并原子写入 `/tmp`；
- 只统计当前 LAN 前缀，地址换 owner 时重新建立累计基线。

但这些防线还不足以宣称适合长期运行在低内存路由器上：

- 每次 `DeviceTraffic.Snapshot` 都调用完整 `DeviceInventory.Snapshot`，后者会读取 ARP/DHCP/NDP/host hints/Wi-Fi、重新聚合并写历史文件；当前 3 秒轮询会放大这些工作；
- netlink 路径先取得完整 conntrack dump，`/proc` 回退也先构造全部 flow slice，单次峰值内存随连接表增长；
- `DeviceTraffic.totals` 没有 TTL/容量淘汰，随机 MAC 或长期设备 churn 会持续留下 device ID；
- 采样请求 channel 不感知调用方 context，慢采样和并发请求可能积压 HTTP goroutine；
- OUI 数据在进程启动时异步加载到多层 Go map，并常驻整个进程；尚未单独测量它的堆占用；
- 既有 2 小时模拟只覆盖 20 个固定设备，不覆盖大量 flow、随机身份 churn、真实文件/ubus/命令开销和 24 小时墙钟运行。

因此 M12 是新增长期历史、DNS、连接明细和复杂策略之前的强制门槛。

## 4. M11：名称语义、输入与写入安全

### 任务树

1. **名称模型冻结**
   - Device Alias：用户展示名，支持安全 Unicode、中文、空格和常用符号；
   - DHCP Hostname：可选的网络主机标签，仅允许 ASCII `a-z`、`0-9`、中间连字符；
   - 原始客户端 Hostname：只读观察值，不直接回写；
   - 先冻结 UI 用词：现有静态地址表单只称“DHCP 主机名”；独立“设备备注名”入口在 M13 交付。
2. **权威校验**
   - DHCP Hostname 规范化为小写单标签，1～63 字节，不能以连字符开头/结尾；
   - 禁止中文、空格、点、下划线、引号、反斜杠、控制字符和换行；
   - Device Alias 设字符/字节上限，存储前验证 UTF-8，输出时正常转义；
   - 前端即时提示，后端重复执行同一规则并返回字段级错误。
3. **安全配置写入**
   - 删除静态地址、DHCP tag、floatip 等路径中对用户输入的 Shell 字符串插值；
   - 使用参数化命令、直接 UCI 库调用或严格序列化 Adapter；
   - 保存前运行 UCI 结构预检和 dnsmasq 配置检查；失败不 reload 服务；
   - reload 后验证 dnsmasq 存活，失败自动恢复快照。
4. **分类一致性**
   - 将已确认的 ASUSTek/ASUS 厂商默认类别改为网络设备；
   - `source=manufacturer_default`，不得声称具体型号；
   - 更强型号/名称规则和人工修正继续优先；
   - 同步后端 classifier、fixture、前端兼容适配器和品牌说明。
5. **交互文案**
   - 当前静态地址表单的“设备名称”立即更名为“DHCP 主机名”；
   - DHCP Hostname 进入高级项，明确“用于局域网解析，仅支持英文、数字和连字符”；
   - Device Alias 的独立持久化入口留到 M13，不再临时复用 DHCP host 字段；
   - 不自动把中文 Alias 转拼音或 Punycode，避免不可预测名称。

### 明确验收标准

- 当前观察到的 `客厅电视`、`小明的 iPad` 等 Unicode 名称可以安全展示，但不会被自动回写 DHCP；
- 同样文本提交为 DHCP Hostname 时前后端均拒绝，拒绝前 `/etc/config/dhcp` 哈希不变；
- `living-room-tv` 接受，`-tv`、`tv-`、`tv.local`、`living_room`、引号、换行和 64 字节标签拒绝；
- fuzz/表驱动测试覆盖 Unicode、Shell 元字符、UCI 元字符、控制字符和最大长度，不产生命令执行或配置截断；
- dnsmasq 预检失败时旧进程继续运行，配置恢复且页面显示具体字段错误；
- ASUSTek 基准设备显示 ASUS 网络设备图标/类别，详情仍显示原始厂商和“厂商默认类型”；
- M1～M10 原有静态地址、分类修正、限速和断网测试无回归。

### 不做

- 本阶段不创建 Gateway Profile，不合并旧规则页，不增加长期流量历史。

## 5. M12：设备统计性能、容量和可观测底座

### 任务树

1. **建立真实性能基线**
   - 分别测量进程启动、OUI 数据加载、首次 Inventory、稳态 Inventory、conntrack 采样和 DeviceTraffic；
   - 样本覆盖 20/256/2048 台设备与 1k/20k/系统上限 flow；
   - 记录 RSS、Go heap、总分配、GC、CPU、响应 p50/p95/p99 和响应大小。
2. **解耦发现与遥测频率**
   - DeviceTraffic 不再每 3 秒直接触发完整 `DeviceInventory.Snapshot`；
   - 建立有 TTL、版本和失效事件的只读 Inventory cache；
   - DHCP/ARP/NDP/Wi-Fi 等昂贵 Adapter 按各自合理频率刷新，多个请求共享同一次刷新；
   - 并发首次请求使用 singleflight 或等价机制防止命令/ubus 风暴。
3. **限制状态与内存**
   - 修复 `DeviceTraffic.totals` 对历史 Device Identity 只增不减的问题；
   - 所有 map/ring/event/history 明确上限与 TTL；淘汰时输出降级原因；
   - 单独测量现有 1.9 MiB/55,134 行 OUI 文件解析前后的常驻内存；若超过预算，采用紧凑表/字符串去重，并仅在不会拖慢首次清单的前提下考虑惰性加载；
   - 设备历史 JSON 仅变化后节流、原子写入 `/tmp`。
4. **降低 conntrack 峰值**
   - 评估 netlink dump 和 `/proc/net/nf_conntrack` 回退的峰值分配；
   - `/proc` 路径改为边读边聚合或有上限解析，避免先保存全部 flow；
   - API 请求不能无限堆积在单一采样 channel；支持 context 取消、合并并发请求和超时；
   - 保留 3 秒默认采样，但根据消费者与页面可见性启停。
5. **运行态诊断**
   - 输出不含设备隐私的内部指标：设备数、flow 数、缓存大小、淘汰数、采样耗时、失败数、最后采样；
   - 指标页只在高级诊断展示，并设频率限制。

### 明确验收标准

- 3 秒 DeviceTraffic 轮询期间，完整 Inventory Adapter 实际调用频率不高于设计 TTL，且同一时刻最多一个刷新；
- 设备历史内容无变化时 10 分钟内文件 mtime 不重复变化；
- 100,000 次随机身份 churn 后 `totals`、addresses 和 Inventory history 均不超过各自 2048 上限；
- 20,000 flow `/proc` 样本可流式完成，峰值堆内存不随“保存全部 flow 对象”线性增长；
- 请求取消后阻塞的采样请求在 1 秒内退出，不遗留 goroutine；
- OUI 索引增量常驻堆目标不超过 8 MiB；若基线已低于目标，则不得回归超过 10%；
- 256 设备、20,000 flow 的 `DeviceTraffic` p95 不超过 500 ms，单次分配量记录为后续回归基线；
- 真机 2 小时活跃页面 RSS 增长不超过 10 MiB；页面关闭后采样停止；
- 原有地址 owner 切换、IPv4/IPv6 聚合、预热/过期/部分失败语义不变。

### 不做

- 不在本阶段持久化跨重启流量历史，也不引入 Bandix/eBPF。

## 6. M13：独立 Device Profile 与设备资料交互

### 任务树

1. 建立 `DeviceProfile` Module，Interface 只提供 Get、Patch、Reset；
2. 以持久 Device Identity 保存 Alias、Device Group 引用和品牌/类型人工覆盖；品牌修正必须保留原始 Manufacturer 和修正来源；
3. boot-local 身份的 Alias/分类只保存到本次开机，并明确提示；
4. 将现有分类覆盖迁移到统一存储，设置容量、原子写入、损坏降级和版本迁移；
5. 设备详情身份区提供改名、修改类型、恢复自动；列表即时同步；
6. 原始 DHCP Hostname、厂商和识别证据保留为只读诊断信息。

### 明确验收标准

- 修改 Alias 不创建静态租约、不 reload dnsmasq，不改变 DHCP/firewall/eqos/floatip 哈希；
- 持久 MAC 身份重启 Quickstart 后仍保留；boot-local 身份明确只在本次开机有效；
- 损坏存储返回 partial 状态但设备清单仍可用；
- 2048 条上限、重复提交、并发更新和原子恢复测试通过；
- 用户从详情改名不超过 2 个主要操作，中文名称在三档视口不破坏布局；
- 人工类别和 Alias 不参与设备身份合并、IP owner 或遥测归属。

## 7. M14：Gateway Profile 后端基础

### 任务树

1. 建立 `GatewayPolicy` Module 的 ListTargets、PlanAssignment、ApplyAssignment、References Interface；
2. 把本机、上级路由、旁路由、浮动网关、自定义网关统一为 Gateway Target；
3. 内部 Adapter 负责 DHCP Policy Tag 和 option 3/6，外部契约不暴露 tag ID；
4. 读取并兼容已有 `t_auto_*`、自定义 tag 和 host 引用，不破坏现有配置；
5. 增加目标同网段、IP 冲突、可达性、DNS 行为、引用数量和删除影响预检；
6. 给 target 与 assignment 增加稳定 ID、版本和 desired/effect 状态。

### 明确验收标准

- 所有现有自动/自定义 DHCP tag 可无损映射为 Gateway Target，未知 option 以 unsupported 保留而不是丢弃；
- Plan 返回将修改的 host/tag/option、受影响设备、是否需续租和回滚点；只读 Plan 不改变文件；
- 有设备引用的 target 不能直接删除，必须先迁移或明确解除；
- 相同 assignment 重复提交无额外 UCI 写入；中途失败恢复 host/tag 和 dnsmasq；
- 旧静态分配接口继续读写同一配置，兼容测试通过；
- 2,048 设备引用扫描满足 M12 性能门。

## 8. M15：设备“上网路线”完整交互

### 任务树

1. 详情中新增“上网路线”，默认只显示跟随网络默认、本机、上级、旁路由、浮动网关等用户名称；
2. 从静态地址高级项移除裸 DHCP 标签输入；调试信息只读显示内部 tag；
3. 地址保留与上网路线可独立修改，也可一次提交为同一个事务；
4. 保存后显示 pending renewal、active、unverifiable、error；
5. 列表规则摘要增加路线异常/浮动网关降级，但不增加默认列；
6. 提供安全的重新获取租约说明，不自动断开用户设备。

### 明确验收标准

- 用户无需看到“DHCP 标签、option 3/6”即可让设备选择五类路线；
- 从详情到完成路线选择不超过 3 个主要操作；
- 保存成功但终端未续租时明确显示“等待设备重新获取地址”，不能误报“已生效”；
- 地址保留和路线联合提交任一失败时全部回滚；
- 经典列表、静态规则台账和新详情读取结果一致；
- 网关不可达、目标被删除、DHCP 关闭均显示可行动原因。

## 9. M16：浮动网关向导、状态与演练

### 任务树

1. 建立 `FloatingGateway` Module，翻译用户职责与插件 `main/fallback`；
2. 三步向导：节点职责、地址与检测、变更预检；
3. 采集进程、虚拟 IP 持有、对端可达、URL 探测、配置版本和最近切换；
4. 状态归一为 disabled/starting/healthy/degraded/failover/error；
5. 支持两个节点配置导出/导入或一次性配对信息，检查角色互补和参数一致；
6. 提供显式故障切换演练、停止条件和恢复；演练不默认自动运行；
7. 与 Gateway Target 引用联动，关闭/改 IP 前展示受影响设备并生成迁移计划。

### 明确验收标准

- 用户界面不出现裸 `main/fallback`，而显示“优先服务节点/故障接管节点”；
- 可以回答当前虚拟 IP 在哪台节点、对端是否可达、外网检测是否成功、上次为何切换；
- 同网段、IP 占用、角色冲突、URL 无效和插件缺失均在写入前阻止；
- 受控演练中 B 正常时虚拟 IP 在 B，B 故障后 A 在目标时间内接管，B 恢复后行为符合策略；
- 演练全程记录时间线并可一键恢复，测试结束网络/DHCP/防火墙哈希符合预期；
- 浮动网关被设备引用时，关闭或改 IP 不会留下悬空 DHCP tag。

## 10. M17：统一网络规则台账与导航收口

### 任务树

1. 一级导航改为设备、网络规则、网络服务；保留旧路由兼容跳转；
2. 网络规则统一展示地址保留、上网路线、联网权限和限速；
3. 支持按类型、状态、设备、分组筛选及批量迁移/删除；
4. 离线设备和孤立规则继续可见，并提供修复/重新绑定；
5. 同一个 resolved policy view model 同时服务详情与台账；
6. 建立策略来源和 Policy Precedence 解释器，为下一阶段分组规则做准备。

### 明确验收标准

- 现有静态分配与限速台账的添加、编辑、搜索、删除、批量删除、离线维护全部有新入口；
- 旧 URL 可预测跳转或通过开关恢复，不出现 404；
- 详情与台账对同一设备的最终规则完全一致；
- 孤立 MAC/IP/tag 规则不会静默丢失；
- 批量操作先显示数量、冲突和回滚范围；部分失败不留下不可解释的混合状态；
- 用户完成单设备任务不需要进入规则台账。

## 11. M18：Device Group、策略优先级与定时规则

### 任务树

1. 建立用户 Device Group，与 DHCP Policy Tag 完全分离；
2. 支持设备加入多个展示分组，但策略分组采用明确限制或优先级；
3. 定义全局 → 分组 → 设备的 Policy Precedence，并处理 allow/block、速度和路线冲突；
4. 新增定时联网与定时限速，规则由后端根据路由器时区计算；
5. 支持星期、跨午夜、临时暂停和下次生效时间；
6. UI 显示最终值、来源和“为什么生效”。

### 明确验收标准

- 建立“儿童设备”分组并一次设置睡眠时段，组内设备按时阻断、按时恢复；
- 跨午夜、夏令时/时区变化、多个重叠规则和路由器重启测试有确定结果；
- 前端时钟错误不改变后端策略真值；
- 单设备例外、分组规则和全局默认冲突时，UI 能显示最终规则及来源；
- 删除分组不会删除设备或静默删除仍需保留的单设备规则；
- 调度器状态、计划数量和事件历史均有上限，不产生每设备 goroutine/定时器。

## 12. M19：历史流量、流量配额与可选 Adapter

### 任务树

1. 建立 `TrafficInsights` Module，与实时 `DeviceTraffic` 分离；
2. 定义实时/小时/天/月分层聚合、保留期、精度和磁盘预算；
3. 提供本地轻量 Adapter；评估并可选接入 Bandix，不让核心依赖 eBPF；
4. 支持设备日/周/月/累计配额及达到配额后的通知/阻断行为；
5. 区分速度上限、计划限速和流量配额；
6. 历史图表进入详情，列表只显示必要摘要。

### 明确验收标准

- 没有 Bandix、内核不支持或硬件卸载开启时，设备、地址和规则核心功能完整可用；
- 支持时可查看今天、本周、本月趋势，重启后按配置保留；
- 存储有固定预算、分层压缩和写入节流；达到预算淘汰旧桶，不继续增长；
- 配额边界、周期重置、时区变化、计数器回绕和 IP owner 变化不串量；
- 20 台设备 30 天模拟数据的文件大小、查询延迟和写入次数符合预算；
- Bandix Adapter 的版本、内核、网口和卸载限制明确显示为 capability，不自动修改系统卸载设置。

## 13. M20：IPv6 等价性、网络洞察、事件与高级集成

### 任务树

1. 在目标固件验证后增加 DHCPv6 静态保留和 IPv6 策略能力；
2. 连接/DNS 洞察通过可选 Adapter 进入设备详情和高级“网络洞察”；
3. 增加受限并发的 HTTP/HTTPS 管理入口探测，并明确安全风险；
4. 建立 Audit/Event Module，记录策略修改、地址冲突、上线/离线、网关切换和配额事件；
5. 支持用户配置的新设备/故障切换 Webhook，默认关闭并保护隐私；
6. 增加策略导出/导入、预览、版本校验和恢复；
7. 为来宾/IoT 分段与多 WAN/策略路由建立独立 Adapter，明确它们不等于 DHCP 网关分配；
8. 为离线 OUI/识别规则建立带来源哈希、正反例、精确 MAC override 和回滚的更新流程。

### 明确验收标准

- IPv6-only 设备能设置受支持的地址/访问策略；不支持时 capability 明确且不展示假控件；
- DNS、连接、Web 管理入口均不进入默认六列，页面无信息过载；
- 探测有并发、超时、目标网段和端口白名单，不允许 SSRF 到非 LAN 地址；
- 审计按环形容量淘汰，可按设备解释最近规则和网关变化，不记录敏感 DNS 正文除非用户显式开启；
- Webhook 失败有退避和队列上限，不阻塞核心策略；
- 导入先 dry-run，冲突或版本不兼容时零写入；
- VLAN、多 WAN 不支持的设备安全降级，单 LAN 用户不增加默认配置复杂度。

### 任务树
