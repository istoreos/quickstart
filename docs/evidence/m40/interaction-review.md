## 3. 必须先修复的问题

### P0-1：LuCI 全局 `header::after` 污染组件

组件内部使用语义化 `<header>`，但 LuCI 主题为所有 `header::after` 注入绝对定位的蓝色块。该伪元素覆盖页面标题、分组标题和局域网设置标题，且 `pointer-events: auto`，因此不仅难看，还会拦截按钮。

验收目标：设备管理作用域内所有内部标题均无主题伪元素；桌面、平板、手机标题与操作完整可见；所有主按钮可用真实 Playwright 点击完成，禁止以 DOM `element.click()` 绕过。

### P0-2：设备资料图标领域键使用错误

后端返回 `resolvedKey="category:computer"` 和 `assetKey="computer"`。编辑器却把 `resolvedKey` 当作 `DeviceIconKey` 查询文案，得到 `undefined`，随后 `vue-gettext` 调用 `.trim()` 抛错，设备资料区域完全空白。

正确契约是：

- `resolvedKey`：识别证据或命中规则的领域键，例如 `brand:asus`、`category:computer`；
- `assetKey`：前端实际渲染的图标资产键；
- `preferenceKey`：用户手工选择的图标资产键；
- 自动预览使用 `assetKey`，手工预览使用 `preferenceKey`，不得相互替代。

验收目标：三种视口均显示别名、设备类型、图标模式和图标库；品牌自动识别、类型回退和手工选择三条路径都有组件测试与浏览器测试。

### P0-3：关键交互必须由真实点击通过

审计脚本保留 DOM 点击仅用于继续采集后续页面，但任何 `interactionFailures` 都必须使审计失败。正式验收不允许把脚本绕过视为用户可操作。

## 4. 信息架构与产品闭环评审

当前一级结构“设备 / 分组与计划 / 局域网设置”是正确的；局域网设置下的“网络服务 / 上网路线 / 规则台账”也符合用户的任务模型。问题主要发生在状态表达和跨页面一致性。

### 设备

优点：设备、在线状态、地址、连接、实时流量和策略集中在一屏；搜索、筛选、排序简单；详情抽屉避免离开当前上下文。

需要收口：

- “已控制”容易被理解为被封禁，改为“已设置”，并给出规则数量或最重要规则摘要。
- 列表的策略摘要必须覆盖地址预留、上网路线、限速、联网权限、时段、额度、分组来源。当前列表只消费有限规则，可能出现详情已配置路线而列表显示“无策略”的矛盾。
- 多地址的 `+N` 必须可展开并有可访问名称；设备重名时 IP/MAC 保持清晰可扫读。

### 设备详情

推荐保持四段任务结构：

1. 概览：只读状态和最重要的当前结果；
2. 设备资料：用户称呼、局域网主机名、类型、图标；明确区分“显示名称可中文”和“DHCP 主机名仅安全字符”；
3. 网络与上网：地址预留和上网路线，展示“期望 / 已应用 / 已观测”状态；
4. 用量与规则：速率、限速、联网权限、时段和额度。

手机端页签可横向滚动，但首尾标签被裁切且没有滚动提示。应优先采用两行 2×2 页签，或提供渐隐提示；`summary`、复选框等目标区域至少 40px，推荐 44px。

### 分组与计划

“一组设备共享规则”的价值明确，规则来源和覆盖关系也值得保留。表单应继续使用开关渐进展开，但需调整：

- “优先级 10”属于实现概念，默认隐藏到“冲突处理/高级设置”；常规用户通过拖动顺序理解优先关系。
- `0 / 2048` 改为“已选择 0 台设备”，内部上限不作为主要信息。
- 所有文案跟随当前语言；同一表单不得混用中英文。

### 网络服务

DHCP 与限速服务归入此处合理。两类写操作应采用一致流程：编辑 → 影响预览 → 明确应用 → 结果反馈。能力未安装时保留解释和安装引导，但不显示不可用的伪操作。

### 上网路线

自定义网关与浮动网关并列是合理的。已配置的浮动网关不应仍默认展示三步初始化向导，否则看起来像未完成。默认应显示状态卡：配置节点、浮动 IP、当前承载节点、健康状态与最近切换；点击“编辑配置”后再展开向导。

路线命名应可辨认，默认名可由 IP 生成，但重复的“自定义网关”不能成为最终展示名称。对于旁路由角色，当前阶段继续只读引导；是否可编辑仍由本机 DHCP 分配权决定。

### 规则台账

只读汇总、检索、筛选、发现离线或孤立规则的定位正确；新增设置继续从设备或分组进入，避免形成第二套编辑入口。

手机端不应只依赖横向表格滚动。建议每条规则改为卡片：设备与状态在首行，规则摘要和来源在第二行，修复/移除动作在末行。批量选择目标尺寸需达到 40px。

### 历史设置接管

当前迁移卡在三个设置页重复占据首屏，同时旧规则已经能在路线和台账中查看，会形成“已经可管理”与“尚未接管”的语义矛盾。

统一为一次性、可收起的“待整理设置”提示：只显示数量、风险和入口；详细项目、冲突处理、预览与确认放到独立抽屉。接管完成后永久退出日常主流程。

## 5. 跨层一致性规则

| 领域事实 | 唯一来源 | 列表/详情/台账要求 |
| --- | --- | --- |
| 设备身份 | 设备清单 + 用户资料 | 名称、品牌、类型、图标一致 |
| 设备策略 | 统一有效策略投影 | 三处显示同一规则数量、来源和结果 |
| 上网路线 | 期望配置 + 应用结果 + 运行观测 | 不把“已保存”误报为“正在生效” |
| 浮动网关 | floatip 配置 + 两节点运行状态 | 明确区分配置正常、承载未知、服务异常 |
| 可编辑性 | DHCP 分配权 + 能力状态 | 主路由可编辑，旁路由只读引导，缺组件给安装引导 |
| 历史接管 | 单一迁移状态机 | 未整理、可整理、有冲突、已完成互斥且可恢复 |

## 6. 推荐收口顺序

1. 修复标题伪元素与设备资料崩溃，建立 P0 浏览器门禁。
2. 建立统一有效策略投影，消除“列表无策略、详情有策略”的跨页面矛盾。
3. 收敛历史设置接管为一次性流程，并统一所有语言文案。
4. 优化已配置浮动网关状态、分组优先级表达和移动端规则卡片。
5. 扩充自动化：读路径可在主路由执行；任何写路径仅在隔离环境或显式维护窗口执行。

完成前两项后，才能进入可用性复验；六类页面在三个视口均无阻断、无异常、无状态矛盾后，才能判定整体交互可发布。
