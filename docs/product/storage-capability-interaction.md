# 存储能力与操作资格

本轮在已经确认的 QuickStart 存储原型上补充能力限制，保留原有布局与 RAID 请求协议。代码位于 `web/src/design`，能力结果、重新检测与拦截均为内存示例；没有新增生产探测接口、安装组件或修改测试机。

## 用户看到什么

- 硬盘、存储池、RAID、任务入口始终保留。能力不足不等于没有资源，也不隐藏已有记录。
- 仅对依赖缺失能力的操作置灰，旁边直接显示原因；手机端不依赖鼠标悬停。折叠的“系统存储能力”提供完整状态与处理建议。
- 普通 EXT4 与 LVM 分开判断。没有 LVM 仍能沿用文件存储；没有格式化工具也不意味着无法读取已经挂载的文件。
- LVM 管理工具、thin-pool 内核能力、LightHost 接入分别检查。没有 LightHost 不应禁用系统应用卷。
- RAID 的系统能力、级别支持、可用成员数量、当前阵列状态分开判断。硬盘不足显示如何补充硬盘；缺内核能力不能提示“插入更多硬盘即可”。
- 已有阵列缺乏可信当前能力信息时，显示“待重新核实”，保留来源与成员信息，不继续使用绿色“正常”作当前结论。
- 新建 EXT4 与扩容 EXT4 分开判断，分别依赖格式化与扩容能力。卷扩容不能只增加块设备容量后就声称完成。
- 恢复点、任务记录与诊断说明仍可查看。归属模块未接入的写入入口继续关闭。

## 状态与话术

| 状态 | 页面行为 | 下一步 |
| --- | --- | --- |
| 可用 | 系统能力允许；还需资源级预检 | 按原流程操作 |
| 正在检测 | 暂停新提交，保留记录 | 等待真实结果，不能超时后自动变可用 |
| 缺少组件 | 关联按钮置灰，指出缺少哪类工具 | 核对当前固件兼容软件包；重新检测 |
| 系统不支持 | 关联按钮置灰，指出内核或平台限制 | 使用兼容固件或其他存储方式 |
| 尚未确认 | 旧后端、字段缺失或结果过期不能当作支持 | 检查版本、接口与新采样 |
| 检测失败 | 明确“失败不代表系统一定不支持” | 检查连接与服务，再检测 |
| 无操作权限 | 禁止修改，保留获授权的只读展示 | 切换有权限的账号 |

“重新检测”不会自动安装软件，也不自动重放原计划。原型重复读取所选示例，只有切换演示配置才改变能力；生产需真实探测。

## 能力与操作对应关系

| 操作 | 所需能力（随后仍需资源预检） |
| --- | --- |
| 新建普通文件分区 | 分区管理、EXT4 格式化 |
| 格式化已有分区 | 对应文件系统格式化 |
| 挂载 / 卸载 | 挂载管理、支持目标文件系统 |
| 创建应用存储与应用卷 | LVM、thin-pool；需要文件系统时另检 EXT4 |
| 准备 LightHost 主机存储 | LVM、thin-pool、LightHost 接入；管理文件另检所需文件系统 |
| 扩容应用卷 | LVM、thin-pool、EXT4 扩容；容量与布局资格另检 |
| 删除应用卷 | LVM、thin-pool；依赖占用与恢复点另检 |
| 创建 RAID | MD/管理工具、所选级别、分区与文件系统准备、挂载 |
| RAID 成员变更 / 恢复 | 对应 MD/管理工具与级别；沿用现有业务检查 |
| SMART 自检 / 保存计划 | SMART 管理能力；单盘协议与权限另检 |

原型在按钮、计划入队、执行前、RAID / SMART 示例传输层分别拦截。排队后能力变化时，应用按钮暂停；即使直接调用模型，执行前仍会停止，不改变布局。已有完成步骤不回滚。

## 生产实现契约（尚未实现）

1. 后端统一返回结构化能力：`state`、`reasonCode`、面向用户的原因、可行处理建议、`sampledAt`、`revision`，并区分全局能力、对象级能力和账号操作授权。具体接口路径随生产 API 设计确定，原型不虚构已存在的接口。
2. LVM 检查工具可执行性、device-mapper 及所需 thin target；内核配置、已加载或可用模块与实际功能证据结合，不以是否出现某个二进制或 `/proc/modules` 一项判定全部能力。不为探测而创建 PV、VG 或测试卷。
3. RAID 检查 mdadm 与 MD、各级别能力；查看运行阵列与潜在可加载模块是不同证据。探测不调用原 Autofix，不清配置、不组装、不重启阵列。
4. 文件系统格式化、扩容、挂载分开报告，按文件系统类型判断。RAID 创建还依赖当前业务的文件系统准备流程。不得把 `mkfs` 存在推断为能够在线扩容。
5. SMART 同时区分全局工具 / 服务能力、单盘或转接器支持、休眠、命令失败与真实健康结果。无工具时可查看授权的历史结果；新的原始查询同样应报告不可用。原型没有覆盖全部单盘协议差异。
6. 只读权限不保证所有日志可读取；生产接口独立鉴权。前端置灰仅用于解释，不能充当后端权限控制。
7. 计划绑定能力修订与资源身份；执行时在资源锁内重新探测资格。组件卸载、权限变化、服务停止或过期结果均可使预检失效。无权限、检测失败、缺字段默认拒绝新写入，并返回可识别错误码。
8. 系统能力不代替设备资格：系统盘保护、稳定身份、挂载 / 应用占用、只读设备、容量、元数据、阵列同步 / 降级、管理归属仍沿用原有检查。已经挂载或运行的应用不因工具缺失就被声称已经停止。
9. 能力不支持时不清除现有配置；资源列表注明数据时间与可信度。接口失败与空列表分开，后端重新上线后重新读取能力与资源，再允许提交。
10. 组件安装 / 固件升级作为独立流程，提示版本兼容、重启影响与用户确认。原型只提供建议，不提供一键安装或动态加载内核模块按钮。

## 验证

- `scripts/review-storage-capabilities.cjs`：能力组合、普通 EXT4 兼容、执行前能力变化、旧 RAID 请求、SMART 与账号限制。
- `scripts/review-storage-capability-ui.cjs`：用途禁用原因、池操作、RAID 操作 / 级别、未知状态、SMART、手机与明暗主题。
- 证据：[模型检查](ui-design/storage-workbench/capability-model-review.json)、[界面检查](ui-design/storage-workbench/capability-ui-review.json)。检查仅针对原型，不代替目标机 LVM / RAID 硬件资格验收。

本轮结果：11 组能力模型检查、7 组能力界面检查通过；TypeScript 和设计构建通过。原 RAID 13 组交互与 7 个原请求契约回归通过。SMART 8 组检查完成，报告仍标注已有首次设备配置缺陷，未将它记为生产问题已解决。
