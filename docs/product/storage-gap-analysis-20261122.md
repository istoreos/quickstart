# 存储产品差距评审：从准备存储到日常维护

日期：2026-11-22。评审基线：quickstart `feat/disk-format` 分支提交 `f978db4`，
已包含当前存储 / RAID 原型、交互文档与浏览器验证材料。

本次用户要求先调研第三方成熟产品，再分析关键交互及技术细节的遗漏。
本文是建议与实施方案，不表示已经新增这些能力，也不改变当前 RAID 业务。
第三方事实见[官方产品调研记录](storage-third-party-research-20261122.md)；
当前交互基线见[场景评审](storage-scenarios-and-implementation.md)和[RAID 接入约定](raid-existing-business-integration.md)。

## 1. 核心判断

当前设计已经能表达“这块空间是什么、准备给谁使用、如何发起操作”。
下一阶段最有价值的是补足“设备出问题时认得准、长操作看得懂、离开页面也知道结果、失败后能继续处理”。
保持现有四个工作区与侧栏，不需要为了参考成熟 NAS 而增加大量顶层页面。

持久任务、依赖检查、容量余量、应用接入在上一轮已经记录，属于待落实能力，不重复包装为新发现。
本轮新增的重点是：硬盘与物理位置的对应、测试和维护的完整结果、非破坏发现与实际恢复的分离、
阵列操作阶段与文件系统容量的区分，以及下文可定位的现有实现细节。

## 2. 借鉴成熟产品的哪些做法

| 参考产品 | 借鉴重点 | 对 quickstart 的取舍 |
| --- | --- | --- |
| Synology Storage Manager | 健康、成员身份、换盘、维护提醒和可处理告警 | 硬盘侧栏提供健康 / 测试入口；告警能定位受影响存储和应用；复用已有 SMART 能力 |
| TrueNAS | 物理盘识别、已有存储导入、维护任务、恢复点与备份的生命周期 | 借鉴识别后再操作及维护结果；ZFS 的校验、自修复和 scrub 不当作 mdadm + EXT4 的现成能力 |
| Proxmox VE | 长任务记录、状态与日志、恢复操作与在线使用的区分、thin 容量管理 | 命令提交结果与后台状态分开；关网页后任务仍可查询；池空间和卷容量分别显示 |
| Cockpit / RHEL web console | 存储拓扑、挂载、设备与文件系统扩展的关系 | 延续“物理来源 → 池 / 阵列 → 文件系统 → 使用者”；按实际支持的模板开放操作 |

上述为本项目的采用建议；每项产品事实、官方链接和不能照搬的能力见配套调研记录。

## 3. 优先补足的交互与实现

优先级定义：P0 是接真实写操作前必须核实或补齐；P1 是日常使用需要；P2 是后续扩展。
这不是要求在 UI 评审期间同时实现全部功能。

| 优先级 / 缺口 | 用户交互方案 | 技术实现重点 | 完成条件 |
| --- | --- | --- | --- |
| P0 认得出是哪块盘 | 标注型号、序列号末位、接口和用途；确认页同时展示稳定身份；支持时才提供定位灯，无灯则给接口 / 位置说明 | 结构化 serial / WWN / by-id，关联当前路径与父设备；重复或缺失身份显式标识；提交后再次解析身份，不长期信任 sdb | 换插槽、设备名变化、桥接器缺序列号时不误用旧计划 |
| P0 操作前能看清占用 | 显示“Docker 使用中”“LightHost 管理”“RAID 成员”等具体原因和处理入口 | 后端重新查 mountinfo、holders、swap、系统根 / overlay、LVM、Incus 归属和并发任务；界面候选不是最终授权 | 绕过前端或计划后设备状态改变时，写操作仍被拒绝 |
| P0 发现已有阵列不等于立即恢复 | 扫描先列出阵列 UUID、级别、识别成员和缺失成员；用户选择后才进入恢复 | 只读 examine / 库存查询与组装、配置提交、启动分开；不能把现有 Autofix 当成只读扫描；冲突和旧成员数据不自动强制处理 | 扫描不会改写现有配置或触发已有阵列重启 |
| P0 扩容分阶段完成 | 显示“成员已加入 → 阵列调整中 → 文件系统待扩展 / 已扩展”，允许查看失败阶段 | 命令错误必须返回；读取 md 实际状态；阵列 / 分区 / PV / LV / 文件系统分别验证；按拓扑决定必要步骤 | 单步失败不显示全部成功，已有成功阶段不盲重放 |
| P0 使用真实容量 | 容量卡片区分设备容量、文件系统容量 / 可用量、卷上限、池数据 / 元数据 / VG 余量 | 文件容量读取 FSSIZE / statfs，不能用块设备 Size 替代；池统计读取 LVM；单位与采样时刻明确 | 块设备已扩而 EXT4 未扩时，界面仍显示真实文件可用空间 |
| P0 thin 容量有处理出口 | 提示空间紧张影响哪些卷，提供归属模块的恢复点清理或受支持扩容入口 | 监控数据和元数据；验证 VG 余量、监控进程、自动扩容及 when-full 策略；验证 discard / TRIM 链路与快照持有 | 写满、元数据满、自动扩容不可用都有可解释状态；不声称删文件立即归还池空间 |
| P0 开机挂载未就绪不能悄悄写系统盘 | 应用显示“等待存储 / 挂载失败”，提供处理入口 | 按 md 组装 → LVM 激活 → 指定 UUID 文件系统挂载 → 应用启动排序；核对实际挂载对象，而非只检查目录存在 | 目标盘缺失或延迟就绪时，Docker / LightHost 不在空目录里另建数据并写满 overlay |
| P1 健康检查入口闭环 | 硬盘侧栏增加“健康与维护”：当前健康、上次测试、计划、结果；未知、休眠、未检测、异常分开 | 接现有 SMART 测试 / 结果 / 计划接口；测试启动成功不等于测试通过；与 RAID 重建、全盘检查避免重 I/O 冲突 | 可查看进行中、完成、失败、已中止结果及时间，而非只有“已启动” |
| P1 阵列维护有记录 | 阵列详情的维护区域显示上次检查、结果、下一次计划；检查与修复分别说明 | 先接 md 一致性检查与结果；不要将 ZFS 自修复承诺移植进来；疑似差异不擅自选择正确副本 | 维护时间、发现的差异和后续动作可追溯，不把无校验信息显示成“数据已验证” |
| P1 离开页面也知道异常 | 首页保留未处理告警；通知可定位对象；确认已读与问题已解决分开 | 按资源 UUID 与事件类型合并 / 恢复，避免每 5 秒通知；支持一种可配置外发通道和测试消息；进程重启不丢关键事件 | 关网页后降级 / 空间紧张仍能送达，恢复后状态能闭环 |
| P1 长任务可继续查看 | 任务记录含对象、阶段、真实进度、日志与下一步；断网显示“查询中断”，不判失败 | 服务端持久记录、资源锁、请求去重；md 内核任务与外部命令任务分别跟踪；重启后重新核对事实 | 多标签不重复执行，刷新后查到同一任务；没有进度来源时显示阶段而非虚构百分比 |
| P1 替换与重新加入不同 | 分别提示“原盘重新加入”和“使用新盘恢复”；明确哪些操作会清空目标盘 | 比较阵列 UUID、成员角色、事件信息、实际可用扇区和逻辑扇区；已有 Recover 的清空语义不能冒充原盘无损重新加入 | 识别旧成员冲突、替换盘略小、只读、USB 等情况，有明确处理原因 |
| P1 读取失败不是无设备 | 卡片保留上次状态并标注时间 / 已过期；读取失败给重试；未知时禁写依赖动作 | 单资源健康与库存读取状态分开；失败不覆盖为空数组，不继续宣称旧 clean 状态为实时正常 | 拔盘、API 失败和确实无阵列呈现不同结果 |
| P2 恢复点与备份有生命周期 | 显示覆盖对象、应用一致性、保留期限、最近备份和恢复验证；先支持查看 / 删除受管理恢复点 | 恢复点由所有者创建；冻结 / 解冻超时和 finally 清理；备份只读视图有租约与回收；外部 bind mount 明确排除 | 可恢复到独立位置做验证，过期视图不残留，用户看得懂覆盖范围 |
| P2 用户别名与支持资料 | 允许给设备 / 存储起用途别名；故障页一键导出诊断资料 | 别名独立于设备路径和阵列 UUID；诊断含版本、拓扑、状态、任务步骤及脱敏日志 | 别名不破坏挂载，资料不导出账号、密钥或用户文件 |

定位灯、SMART 指标、TRIM、设备扇区和维护能力均应按硬件 / 工具版本探测，不能作为所有 iStoreOS 设备的固定能力。
不同容量、4Kn / 512e、SMR 或 USB 桥接应建立验证矩阵和适用规则；不照搬其他厂商的全平台禁用清单。

## 4. 本地代码中已确认的技术细节

以下是对指定路径的只读核对，未完成全仓库安全审计，也没有在真实盘复现故障。
“缺少校验”仅指已读操作链中没有看到对应防护，不推断其他组件毫无保护。
业务复用应保留正确用例；已有缺陷另行修复和回归，不因保留旧 UI 逻辑而永久保留。

### T1. 扩充错误有可能被上层当成成功（P0）

[`raid_write_usecase.go`](../../backend/service/raid_write_usecase.go#L97) 的 `Grow` 不返回 error，
忽略 `BatchOutputCmd` 的结果；[`writeflow.Add`](../../backend/modules/raid/writeflow/service.go#L161)
随后返回 nil。建议让 Grow 返回结构化结果 / error，区分成员加入与增长结果，再读回阵列状态。
验收故障点：Add 成功、Grow 失败时，用户能看到部分完成，并且不会再次抹盘添加成员。

### T2. 当前“扫描恢复”实际会改配置和重启服务（P0）

[`mdadmconfig.AutoFix`](../../backend/modules/raid/mdadmconfig/service.go#L51) 发现成员 UUID 后清除现有数组配置，
写入新的条目、提交并重启；[`raidMdadmConfigStore`](../../backend/service/raid_mdadm_config_usecase.go)
的 Commit / Restart 当前也不向上返回错误。
方案是增加只读发现入口，再按用户选择和当前配置生成变更预览；核对阵列身份后提交，读回组装结果。
已有 `/raid/autofix/` 的语义不能仅通过改按钮名称变成“无影响扫描”。

### T3. 新建统一使用 --assume-clean，需要核实适用条件（P0）

[`BuildCreateCommand`](../../backend/modules/raid/writecommands/commands.go#L55) 统一传入 `--assume-clean`，
而 [`Erase`](../../backend/modules/nas/diskcommands/service.go#L77) 只清盘头 32 MiB 并重建 GPT，
不能据此证明成员整个数据区满足一致性前提。
上游手册说明该参数用于已知干净的情况，省略初始同步需谨慎；建议核查目标版本和历史设计，
为新建采用经过验证的初始化策略，不让 UI 将跳过同步解读为已验证冗余。
[mdadm 上游手册](https://github.com/md-raid-utilities/mdadm/blob/main/mdadm.8.in)

### T4. 写入路径需要共享的新鲜库存与占用准入（P0）

[`Create`](../../backend/modules/raid/writeflow/service.go#L77) 会查路径与分区，
[`Add`](../../backend/modules/raid/writeflow/service.go#L161) 直接 Erase 所传成员；
[`Recover`](../../backend/modules/raid/writeflow/service.go#L189) 在未使用成员检测分支时也会清空目标。
[`ValidDevicePath`](../../backend/utils/device_path.go) 明确只是命名空间检查。
当前写流程 Disk / Partition 投影也不携带完整系统 / 所有权 / holders 信息。
建议在这些业务入口共用 `ValidateTarget`：系统与应用依赖、成员资格、稳定身份、只读、扇区和容量、资源锁，
并在锁内重新核对。鉴权和 shell quoting 不能替代设备资格判断。

### T5. 文件系统容量和块设备容量目前没有充分区分（P0）

[`BuildPartitionInfo`](../../backend/modules/nas/diskstatus/service.go#L135) 以 `SizeInt` 计算 Total 和 Usage，
虽然库存已读取 `Fssize`。扩容后 FS 未增长时，这会影响文件容量展示。
方案：分别返回 blockBytes、filesystemBytes、usedBytes、availableBytes 与来源；
从真实分区表获取未分配范围，不将单一容量差值用于创建分区的写入决策。
文件系统内空闲、thin-pool 可用和 VG 空闲继续分别统计。

### T6. 身份信息已有基础，但未结构化贯穿业务（P0）

[`diskinventory`](../../backend/modules/nas/diskinventory/service.go#L42) 读取 Serial，
但主要拼入 DisplayName；通用 DiskInfoRoot 和当前写请求仍以路径为主。
无需重做设备扫描，应补结构化 ID、别名、当前路径与拓扑版本，写前复核并支持重复 / 缺失序列号状态。

### T7. SMART 已实现，主要缺状态语义和新页面衔接（P1）

已有 [`smart/commands`](../../backend/modules/smart/commands/service.go)、
[`smart/config`](../../backend/modules/smart/config/config.go) 和对应 UI，支持测试、结果、属性及计划。
不应再开发另一套 SMART 后端。
但 StartTest 将命令 error 文本概括为“正在运行”，
[`ApplySMARTHealth`](../../backend/modules/nas/diskstatus/service.go#L236) 又将非 PASSED 统归警告。
建议保留原始输出和退出状态，区分已启动 / 执行失败 / 不支持 / 休眠 / 未知 / 检测异常，
将现有测试结果与计划接入硬盘侧栏，再处理维护冲突调度。

### T8. RAID 读取失败尚无面向用户的过期状态（P1）

[`getRaidList`](../../web/src/pages/raid/index/index.vue#L110) catch 目前只输出 console，
原数组可能继续保留，而新卡片依据它显示状态。
建议共享控制层增加 readState、sampledAt、lastError；保留上次数据并标过期，限制依赖实时资格的写操作。
不能简单把失败当作空列表或继续显示实时“正常”。

### T9. 当前磁盘状态 API 不是完整物理库存（P0）

[`diskstatus.ShouldIncludeDisk`](../../backend/modules/nas/diskstatus/service.go) 会排除已识别的 RAID 成员，
`ShouldIncludePartition` 还过滤 kernel、`/rom` 和部分小分区。
如果直接将此结果用作全局硬盘布局，会看不到部分成员或受保护区域。
建议保留当前 API 的兼容投影，新增完整库存读取：原始设备和所有分区、MD 成员关系、LVM 及 holders，
再派生首页摘要与操作候选。写入保护依赖完整库存，不能依赖首页过滤后的列表。

## 5. LVM、MD 与 Incus 的技术底线

- MD 的同步、恢复、检查等状态有独立信号，进度应读实际完成量；检查结果和数据正确性不是同一结论。
  维护检查还需要告知可能的 I/O 影响和行为差异。
  [Linux MD 官方文档](https://docs.kernel.org/admin-guide/md.html)
- 自动扩容需要实际 VG 余量与监控链路；删除文件不保证池块释放，快照和 discard 会影响回收。
  VG 配置备份也不能当作 thin 元数据或文件备份。应记录目标设备的监控、元数据备份 / 恢复与满池策略。
  [LVM2 上游 lvmthin 手册](https://github.com/lvmteam/lvm2/blob/main/man/lvmthin.7_main)
- LightHost 的 Incus 存储继续遵守其所有权；系统 Docker / 沙箱卷使用自己的管理边界，
  工作台统一观察，不直接写入 Incus VG。 [Incus LVM 文档](https://linuxcontainers.org/incus/docs/main/reference/storage_lvm/)
- RAID5/6 的扩充 / reshape 需验证目标 mdadm、内核、布局与断电恢复条件；必要的备份与恢复材料独立保存，
  不能因 GUI 有“扩充”按钮就宣称支持任意在线容量变更。
  [mdadm 上游 Grow 说明](https://github.com/md-raid-utilities/mdadm/blob/main/mdadm.8.in)
- iStoreOS 使用自己的启动与热插拔机制；不能直接照搬其他发行版的 systemd 服务配置。
  应核验实际 mdadm / LVM / thin 工具和内核模块、监控服务、block-mount / procd 的配合。
  固定等待一秒不等于设备已就绪；写分区表后还需核对内核识别的布局，不能在重读失败时假定立即生效。

## 6. 最小实施方案

保持四个工作区：硬盘与分区、存储池与卷、RAID、任务记录。
硬盘侧栏补健康与物理身份；阵列侧栏补维护、真实任务状态及恢复预检；
池侧栏补容量处理和恢复点归属入口；首页继续显示少量需关注项。
通知设置和维护计划放在现有设置 / 详情区域，不另造一套 NAS 导航。

实现顺序建议如下：

1. **先修事实与结果。** T1～T6 逐项核实与修复；保留已有 RAID 用例和接口，
   将新鲜库存校验和资源锁放进共用服务，界面不各写一遍规则。
2. **再接日常维护。** 接已有 SMART 与结果、只读发现、异常 / 过期状态、去重通知，
   把健康与检查结果留在对应资源详情里。
3. **最后补后台生命周期。** 有界串行任务、持久结果、重复请求保护、重启后核对。
   现有 [`installjob`](../../backend/modules/app/installjob/jobs.go) 的锁与结果记录可以借鉴，
   但它是安装专用实现，不是可直接运行 RAID 的通用引擎。先做小型存储任务适配器，避免建设大型编排平台。
4. **扩展恢复点 / 备份。** 沿归属模块提供一致性与只读视图，设计保留、回收和异地恢复验证；
   不以快照替代备份，不以 RAID 检查替代文件内容校验。

新增持久结果与任务存储应放在启动可用、受保护且容量有界的位置；
不能依赖当前正在被卸载 / 重建的目标盘才能读取恢复状态，也不能无界写满系统 overlay。
操作记录包含版本、稳定对象身份、已完成阶段、工具退出结果与时间，重启后重新发现实际对象。

## 7. 验证方案与明确后置能力

首先使用可丢弃的 QEMU 虚拟盘验证故障，不直接拿业务盘做破坏性验收：
换设备名、重复 UUID、恢复旧成员、容量略小替换盘、Add 成功 / Grow 失败、重启中断、
扫描发现冲突、API 读取失败、满池、元数据紧张、文件系统未扩容、TRIM 未生效、
SMART 命令失败、两个标签同时提交等情形，都应显示真实结果且不盲目重放写操作。
涉及 mdadm、LVM、procd / block-mount 的启动顺序还须在目标 iStoreOS 版本验证。

本轮不建议增加任意 RAID 级别转换、跨 VG 自由组合、ZFS 式自修复承诺、复杂热备自动换盘、
存储加密全生命周期或强制恢复按钮。它们可单独规划，不能以“其他 NAS 有”作为当前产品必须全部实现的依据。
本次没有修改现有后端、推送代码或在测试机格式化任何硬盘。
