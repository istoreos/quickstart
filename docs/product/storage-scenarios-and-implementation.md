评审日期：2026-11-21。评审对象为 `/storage?variant=A` 的 quickstart 产品原型、
`web/src/design/` 中的内存模型，以及现有 NAS / RAID 后端入口。
[参考产品与采用理由](storage-interaction-references.md)单独记录。

2026-11-22 更新：RAID 的 UI 与交互重新设计，业务处理与接口继续复用已有实现，详见
[现有 RAID 业务接入约定](raid-existing-business-integration.md)。此前对 RAID 的独立流程与阶段限制已撤回；
下文新的计划协议、统一清空确认与任务持久化要求面向分区 / LVM，不替换当前 RAID 业务；RAID 的界面确认可以按新设计调整。

2026-11-22 后续实施：新增健康/维护/只读发现/过期/挂载等待/任务阶段/告警生命周期等交互，

## 1. 评审结论

保留「首页摘要 → 硬盘与存储 → 点选对象操作」的结构，以 A 多盘布局作为正式设计基线。
B、C 用于比较，不建议第一版同时维护三套正式界面。

普通文件存储、LightHost 主机存储、系统应用存储可并存。用户选择用途，系统生成受支持布局。
统一展示所有设备，但每个资源只有一个写入管理者。

**当前原型覆盖了主要操作演示，但尚未完成全部日常场景闭环。** 必须补齐的部分包括：
创建后的使用入口、应用迁移与失败恢复、依赖检查、真实容量准入、异步任务续看和外来存储识别。
本轮是设计评审和实施约束归档，没有接通真实磁盘操作，也没有修改原型运行行为。

## 2. 术语和第一层操作

| 用户看到的名称 | 用户需要理解的含义 | 按需显示的技术信息 |
| --- | --- | --- |
| 硬盘 | 一块实际设备，显示型号、容量、连接状态和身份信息 | 当前设备路径、序列号 / WWN、接口、扇区大小 |
| 未分配空间 | 还没有划入分区的区域，可以用来新建存储 | 起止扇区和对齐信息 |
| 普通文件存储 | 可以挂载、访问文件和设置共享的存储 | EXT4、UUID、挂载路径 |
| LightHost 主机存储 | 保存虚拟主机的磁盘，由 LightHost 管理 | 独立 VG、thin-pool、Incus 所有权 |
| 系统应用存储 | 可按需分出应用卷的空间 | 系统 VG、thin-pool、数据与元数据占用 |
| 应用卷 | 分配给某项用途的独立空间；创建不等于已接入应用 | thin LV、EXT4、挂载点、消费者、恢复点 |
| 镜像保护 / RAID 1 | 用两块成员盘保存冗余数据的阵列 | 阵列 UUID、成员、同步状态 |

避免使用含义模糊的「Docker 卷」同时指代两个对象：
「Docker 运行数据」表示一个宿主 Docker 实例的 data-root；「容器应用数据」表示某个应用使用的数据目录或卷。
第一版用途向导先处理前者，后者由应用配置分配目录或挂载，后续再设计独立卷。
LightHost 主机内部的 Docker 由对应主机管理，不等于宿主 Docker。

未分配空间的主操作建议叫「准备存储」，复用现有用途向导；普通文件为默认选项。
「自定义分区」作为次级入口，只要求名称和容量，默认 EXT4，不让普通用户填写扇区、PV 或 VG。
当前原型仍并列显示「创建分区」与「设置存储用途」；正式接入时合并主入口以减少重复选择。

## 3. 判断闭环的标准

每个开放操作都必须回答：从哪里进入、会影响什么、完成后去哪里使用、失败后下一步是什么、
刷新或重新登录后如何确认状态。仅有“操作成功”提示不算完整闭环。

下表的「已演示」只指内存原型，不能替代真机验收；「待补齐」表示目前存在断点；
「明确收口」表示第一版不开放写操作，但仍需提供说明或识别结果。

## 5. 应优先补齐的六条交互规则

### 5.1 完成后始终有下一步

结果面板保持简洁，只显示结果、位置和一个主要动作：普通文件「打开文件 / 设置共享」；
应用卷「接入应用」；主机存储「继续设置 LightHost」；RAID「查看同步状态」，文件可用时提供访问入口。
没有文件管理组件时显示可复制路径和安装 / 配置入口，不能用提示文字冒充已经打开文件。
完成结果以重新扫描事实为准，不只依赖命令返回成功。

### 5.2 分区 / LVM 只在最终应用确认一次清空

用途和容量步骤只预览影响；统一的「检查并应用」承担最终身份核对与清空确认。
当前复用用途向导和全局计划各有确认，正式整合时去掉前者的重复输入。
RAID 的旧双确认已改为页面内核对影响；确认后调用原有处理函数和接口。
普通挂载不要求输入设备名；清空与删除展示设备型号、稳定身份、选定范围和具体影响，才要求明确确认。
计划改变影响范围或过期后，原确认失效。

### 5.3 被阻止时显示原因和处理去向

「使用中」必须列出具体使用者，例如“宿主 Docker 正在使用，前往 Docker 存储设置”。
关联对象能跳转；组件不可用时给出说明。系统分区、外来未知结构只读。
没有提供一键强制卸载、强删父分区等绕过入口。

### 5.4 容量只让用户决定必要的部分

名称与容量使用直白的单位说明；显示设备标称容量与可用 GiB 的差异。内部以整数扇区 / 字节计算。
系统决定对齐、分区类型及已验证的元数据 / 应急余量，向导展示扣除后的可分配量。
分别呈现文件系统可用量、卷容量上限、池真实数据占用、元数据占用、VG 可扩展余量。
不超额分配只能降低误用，仍需为快照新增写入保留策略；不能据此保证池永不满。
现有 16 GiB 管理卷、4 GiB 余量和 90% 阈值均是原型示意，不能直接作为产品资格或扩容策略。

### 5.5 任务不会因关网页而丢失

计划在应用前可撤销；提交后转为服务端任务，网页只负责展示。
用户可以回首页或重新登录继续看任务；浏览器刷新前提示尚未提交的计划将丢弃，已提交任务不受影响。
初期不做多客户端草稿同步，也不做执行中的任意取消 / 反向回滚。

### 5.6 异常给出可信出口

空间紧张不能只提示“清理或扩容”。需定位能管理恢复点的模块，或明确当前布局不能在线扩容并引导备份迁移。
数据、元数据告警分别给出原因；删除文件后的空间回收需要实际检测，不自动宣称完成。
RAID 需区分失联、降级、初始同步、重建、失败；原型的固定 35% 不能变成正式进度算法。

## 6. 融入 quickstart 的方式

保留首页卡片的摘要职责：首页显示硬盘数量、主要空间用途和最高优先级异常；完整操作放在独立页面。
原有磁盘、挂载、RAID 和初始化入口进入同一个工作台；磁盘初始化复用用途向导，
RAID 标签使用新卡片和侧栏，继续复用已有管理处理与接口。
Docker / LightHost 从业务页面发起时，向导保留“完成后返回”的来源信息，返回时带稳定结果标识。
新分区 / LVM 入口共用计划规则；RAID 的即时执行和既有格式化 / 挂载保持原业务，不改为新计划协议。

页面沿用 quickstart 的 Card、主题、间距、面包屑、弹窗、反馈和国际化方式；技术资料折叠。
移动端采用纵向硬盘卡片与抽屉详情，保留同一套状态和操作；不用再维护另一套业务流程。
2026-11-22 原型已将原右侧常驻详情改为与局域网管理一致的右侧抽屉：桌面宽 440px，
手机全宽，顶部关闭与底部返回始终可用，内容独立滚动。关闭保留列表位置，
Escape 和遮罩可关闭；后续操作弹窗取消时回到详情，加入计划后收起详情。
相关交互验证见[抽屉检查记录](ui-design/storage-workbench/drawer-review.json)。
第一版四个工作区已经足够：硬盘与分区、存储池与卷、RAID 阵列、任务记录。
恢复点和应用迁移放在归属模块，工作台提供关联入口。

当前集成通过 `vite.design.config.ts` 的首页卡片替换和 `nativeActionBridge.ts` 完成，
只在预览生效。正式接入需加入正式路由、导航和共享数据服务，再替换旧操作入口。
**不要把 Vite 替换、事件桥接、`workbench` 示例单例或模拟 API 当成生产架构。**

## 7. 让未来实现保持简单

### 7.1 一个查询视图，几个明确的写入用例

前端消费统一库存视图：对象 ID、类型、父来源、管理者、状态、容量、依赖、允许操作及阻止原因。
首页和详情从同一服务读取；选中状态和未提交计划保留在页面层。
后端聚合已有分区、挂载、RAID 和 Incus 信息；新增系统 LVM 提供者，不重写所有底层命令。
数据类型和能力列表足以支撑界面，不需要提前做通用存储编排平台。

第一版创建路径限制为：单个磁盘范围 → 普通 EXT4；单个范围 → 专属 VG / thin-pool → 卷；
多块空盘 → RAID → EXT4。已发现的复杂结构仍要正确标识和保护。
不开放任意跨盘 VG、VG 内任意拆池或任意叠加 RAID 与 LVM 的创建器。
未来支持 RAID 上 LVM 时沿用父来源关系，资格验证后再开放该布局模板。

### 7.2 用“预检计划 → 执行任务”承接写操作

建议最小契约如下，名称是设计建议，不是已经存在的 API：

| 接口职责 | 主要输入 / 输出 | 必须满足的规则 |
| --- | --- | --- |
| 查询库存与任务 | 资源、拓扑版本、能力 / 原因、任务阶段 | 读取失败标为未知，不产生“空盘”假象 |
| 预检计划 | 操作类型、对象 ID、容量等参数 → planId、步骤、保留 / 清空范围、影响应用、失效条件 | 后端验证，不接受浏览器传来的 shell 命令 |
| 应用计划 | planId、确认、幂等请求 ID → taskId | 锁定资源后重新验证；重复提交返回原任务 |
| 查询任务 | taskId → 每步结果、实际资源 ID、失败原因及下一步 | 任务跨网页会话保留；完成后重新读取库存 |

先实现串行固定步骤，不做任意依赖图执行器。一个用途向导生成一个复合操作；
同一硬盘一次只有一个布局计划。同一个池内的卷变更按池串行。
RAID 成员替换同时占用阵列及替换盘；卷操作锁定所在池及其物理来源，避免父子层互相破坏。
前端禁用仅帮助解释，最终能力、锁及身份检查必须在服务端。

稳定身份优先使用可用的 WWN / 序列号和分区 / LVM / RAID UUID，并结合容量、布局和父关系复核。
未分配区域用父盘身份和起止范围定位；文件系统 UUID 本身不能作为物理设备唯一证明。
缺少可靠身份、出现重复 UUID、计划后换盘 / 重分区时，让计划失效并要求重新选择。

多步操作用「未开始 → 执行中 → 成功 / 失败 / 未执行」加阶段结果即可。
例如建分区已成功、格式化失败，应报告已存在的新分区，后续按事实重新预检；不能再次抹盘从头执行。
已完成步骤不自动回滚；重建等长生命周期状态与“已提交成员变更”任务分开展示。

### 7.3 现有代码的复用点与边界

| 代码 | 已有职责 | 接入注意事项 |
| --- | --- | --- |
| `backend/modules/nas/routes.go`、`diskinventory`、`partedinfo`、`diskstatus` | NAS 入口、磁盘读取、分区与用途识别 | 作为库存适配基础；补充 LVM / RAID / holders、稳定身份和未知状态 |
| `backend/modules/nas/disklifecycle/service.go` | 挂载、格式化、整盘初始化、尾部空间初始化 | 复用底层能力，不直接把 init 接成任意分区操作；子范围创建 / 删除需独立参数和保留检查 |
| `backend/modules/nas/diskcommands/` | 磁盘命令封装 | 对齐和设备路径规则保留在后端；创建分区必须支持真实 NVMe / mmc 命名和分区表限制 |
| `backend/modules/raid/writeflow/`、`writecommands/`、`inventory/` | RAID 读写与命令封装 | Create 有逐盘擦除，Add 包含成员增长，Recover 另有恢复逻辑；替换成员不能错接扩容入口 |
| `web/src/components/action-disk-*`、`action-raid/` | 现有操作弹窗与业务回调 | 保留必要来源参数，逐步指向统一入口；不能保留绕过新准入规则的写路径 |
| `web/src/design/StorageSetupPrototype.vue` | 用途和容量向导 | 借鉴步骤和话术，容量与设备能力由服务端提供；管理文件位置改用真实目标选择 |

现有 MountPartition 会尝试卸载已挂载目标，并写入 fstab；不能仅因有此函数就认为应用依赖与路径冲突已覆盖。
新布局操作与旧入口共用相同服务端准入规则，不能只给新页面增加保护。
本轮没有完成现有后端的全面安全审计，也没有证明其可直接承接新的计划协议。

## 8. 分阶段范围与上线条件

| 阶段 | 开放内容 | 进入下一阶段前的条件 |
| --- | --- | --- |
| 基础整合 | 真实只读总览、外来结构识别、依赖展示；普通 EXT4 挂载 / 卸载及合格范围的新建 / 格式化 / 删除；统一任务记录 | 身份、系统区、挂载路径、子范围保留、失败恢复与刷新续看验证 |
| 应用存储 | 独立系统池、应用卷、Docker 接入 / 迁移；LightHost 初始化交接和管理文件位置 | 管理文件最小容量及开机可用性经过目标机验证；Docker 迁移失败可按阶段恢复；池告警有处理出口 |
| RAID 整合 | 新 UI 调用已有创建、扩充、移除、恢复、详情、删除和扫描恢复业务 | 确认级别、默认值、候选、禁用与接口保持一致；新卡片、向导和侧栏可完整完成操作 |
| 后续扩展 | LVM 快照工作流、备份只读视图、更多拓扑 | 各功能有完整生命周期及资源回收；与现有功能相同的依赖和任务规则 |

RAID 不重新制定只开放某一级别的阶段门槛；现有支持范围及接口作为接入基线。
新增分区 / LVM 能力仍可通过后端能力列表逐项开放。
沙箱 LVM、无损缩容 / 移动、在线转换文件系统、任意 RAID 级别迁移和强制修复不纳入本轮实现范围。

## 9. 验收清单与已有证据

第一版至少验证：已有 EXT4 文件与 UUID 保留；新建只影响所选范围；受保护区字节范围不变；
挂载路径冲突可解释；应用占用时不能卸载 / 删除；换盘或布局变化使计划失效；重复请求只执行一次；
跨层操作不会并发破坏；每一步失败都显示实际残留状态；断网、刷新、服务重启后可恢复查询；
创建后的使用入口能真正完成业务交接。涉及启动和持久化的路径需补充整机重启验收。

RAID 还需验证新建初始同步、成员替换容量、失联盘重现、重建失败 / 完成及开机组装。
LVM 还需验证卷满 / 池满 / 元数据紧张、文件系统扩容失败、快照回收和所有权边界。
Docker 还需验证迁移前、复制中、切换后和启动失败四个阶段的恢复行为及旧数据保留。

已有[浏览器检查记录](ui-design/storage-workbench/browser-review.json)覆盖 14 组交互，
[首页集成检查](ui-design/storage-workbench/home-integration-review.json)覆盖 3 个首页入口；
证据中的 `writes: []` 表示没有真实写入。它们用于验证原型，不替代上述真机与故障验收。
其中旧 RAID 计划流程的检查已被本次复用方案取代，当前 RAID 以
[新版业务契约检查](ui-design/storage-workbench/raid-redesign-review.json)为准，不再将旧流程记录作为当前行为证明。

本轮新增发现的原型限制也应作为后续修改输入：卷与池的排队冲突尚未完整按祖先资源归并；
原独立 RAID 修复规则已随流程移除，改为复用既有恢复组件；已有分区的重新规划可能更换分区编号；
管理文件选择尚未关联真实挂载目标；创建后的跳转和应用消费状态仍不完整。
这些限制不应在正式后端中照搬。
