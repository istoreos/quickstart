# 局域网设备管理 M21～M31：基线冻结、P0 闭环与正式 UI 里程碑

> 状态：M21～M30 已完成；M31 已完成即时验证，但因三次优化后仍有发布门未通过而暂停，详见 `docs/evidence/m31/acceptance.md`  
> 日期：2026-09-25  
> 前置状态：M11～M20 已完成  
> 取代范围：取代旧计划中尚未执行的 M21“迁移与正式发布”；M11～M20 的历史记录与证据继续有效  
> 产品依据：[产品分析草稿](lan-device-management-product-analysis-draft.md)、[低保真交互设计](lan-device-management-low-fidelity-design.md)、[产品、交互与架构基线](lan-device-management-product-architecture.md)

## 1. 总目标

本阶段不继续堆叠功能。先把产品、领域语言、模块 Interface、真实实现和实机状态收敛为一份唯一基线，再进入正式 UI 开发。

完成 M31 时必须同时满足：

1. 只有一份有效的产品与领域基线，其他文档明确标记为历史、研究或被取代；
2. 七个 P0 问题全部关闭，不允许把设计欠账留到 UI 内用条件判断掩盖；
3. 覆盖矩阵逐项追踪“产品需求、原型、后端、正式前端、实机验收”五层；
4. 正式产品采用“设备 / 分组与计划 / 局域网设置”，不再提供经典列表切换；
5. 现有有效配置通过一次性迁移进入新模型，不保留双写和长期兼容页面；
6. 图标、可选能力、DHCP 分配权、上网路线生效状态、任务级事务和分组批量执行形成完整闭环；
7. 256 MiB、512 MiB 和测试设备三档环境通过资源与稳定性验收。

## 2. 七个 P0 与里程碑映射

| P0 | 问题 | 主负责里程碑 | 最终验收里程碑 |
| --- | --- | --- | --- |
| P0-1 | 一级导航和产品结构存在两套定义 | M21、M23 | M30、M31 |
| P0-2 | 旧页面、旧接口和长期兼容策略与最新决策冲突 | M21、M23 | M30、M31 |
| P0-3 | 联网权限错误依赖限速组件 | M25 | M29、M31 |
| P0-4 | 事务范围过大，跨 dnsmasq/firewall/eqos/JSON 无法承诺绝对原子 | M21、M28 | M29、M31 |
| P0-5 | 上网路线缺少从“已保存”到真实终端效果的诚实闭环 | M27 | M30、M31 |
| P0-6 | DHCP 分配权和 Router Context 主要停留在设计中 | M26 | M30、M31 |
| P0-7 | 图标偏好、品牌修正和品牌+类型视觉没有正式持久化模型 | M24 | M30、M31 |

分组批量写入的部分成功、重复服务重载和低内存风险虽然来自 P0-4，但复杂度足够高，单独由 M29 负责。

## 3. 固定执行顺序

```text
M21 唯一基线与领域语言
  → M22 五层覆盖矩阵和验收框架
  → M23 信息架构与一次性迁移契约
  → M24 设备资料、品牌和图标模型
  → M25 能力拆分与安装恢复闭环
  → M26 Router Context 与 DHCP 分配权
  → M27 上网路线期望/应用/终端效果闭环
  → M28 任务级事务与恢复
  → M29 分组批量执行与低资源优化
  → M30 正式 UI
  → M31 实机、约束环境与发布门
```

M30 不得提前。M21～M29 可以修改文档、原型、领域模型、后端、测试和内部前端状态层，但不以临时正式页面拼装替代最终 UI。

## 4. 共同执行协议

每个里程碑开始前输出：

- 该里程碑最终任务树；
- 可观察、可重复的验收标准；
- 修改范围、外部依赖和回滚点；
- 对五层覆盖矩阵中哪些需求行负责。

每个里程碑实现后：

1. 执行自动测试、静态检查、差异检查和该阶段专属测试；
2. 更新五层覆盖矩阵和证据目录；
3. 自检产品语义、交互、正确性、性能、安全和可恢复性；
4. 未达标最多优化 3 次，每次记录失败原因、改变和结果；
5. 达标后自动进入下一里程碑；仅在三次仍失败、新增产品语义决策或需要扩大外部写入授权时暂停。

禁止用以下方式宣称完成：

- 只有原型而无后端契约；
- 只有后端接口而无正式前端；
- 只有自动测试而无要求的实机证据；
- 把 `unverifiable`、`pending` 或依赖缺失显示成“已生效”；
- 用经典页面作为新产品缺失功能的长期补丁；
- 用静默部分成功掩盖跨模块失败。

## 5. 五层覆盖矩阵规范

M22 将现有矩阵升级为以下结构，后续每个里程碑持续维护：

| 字段 | 含义 |
| --- | --- |
| Requirement ID | 稳定编号，例如 `DEV-ID-001`、`NET-PATH-004` |
| 用户任务与验收结果 | 不使用 UCI、tag、Adapter 等实现语言 |
| 优先级 | P0 / P1 / P2 |
| 产品需求 | 基线章节、状态和已确认语义 |
| 原型 | 页面、场景参数、交互状态和截图证据 |
| 后端 | Module Interface、响应契约、自动测试和能力状态 |
| 正式前端 | 页面入口、状态处理、组件测试和可访问性证据 |
| 实机验收 | 固件版本、依赖组合、步骤、期望、实际结果和证据路径 |
| 总状态 | `not_started` / `partial` / `blocked` / `verified` / `not_applicable` |
| 阻塞原因 | 非 `verified` 时必须填写；`not_applicable` 必须有产品理由 |

矩阵规则：

- 五层中任意一层为空或仅写“同上”，总状态不得为 `verified`；
- 原型中的“完整”只代表交互可观察，不代表生产实现完成；
- 后端与正式前端必须引用可运行测试，不只引用源文件；
- 涉及 OpenWrt 状态改变的需求必须有实机验收；纯文档或纯视觉规则可明确标记实机 `not_applicable`；
- 每个 P0 至少包含正常、空、依赖缺失、错误、恢复和重复提交场景；
- 建立校验脚本，检查 Requirement ID 唯一、五层字段完整、证据文件存在及总状态合法。

## 6. M21：唯一产品与领域基线冻结

### 目标

删除文档之间的产品语义歧义，形成后续开发唯一可依赖的基线。

### 任务树

1. 盘点产品分析、架构、低保真、旧里程碑、覆盖矩阵和 `CONTEXT.md` 的冲突；
2. 冻结一级结构为“设备 / 分组与计划 / 局域网设置”；
3. 明确“规则台账”是局域网设置中的批量与离线维护入口，不是一级入口；
4. 冻结迁移原则：一次性读取和迁移现有有效配置，不保留经典 UI、双写或长期旧接口；
5. 修订领域语言：
   - Device Profile 只包含 Unicode 设备备注、人工分类/品牌修正和图标偏好，不包含 Device Group 成员关系或网络策略；
   - Device Alias 与 DHCP Hostname 是两个字段；前者允许中文，后者只允许 dnsmasq 安全的 ASCII 单标签；
   - Internet Access Policy 与 Speed Policy 是两个独立能力；
   - Router Context 描述选定 LAN 的拓扑证据和 DHCP 分配权；
   - Desired Policy、Applied Configuration 和 Observed Effect 必须分开；
6. 冻结三个用户写入任务：设备资料、网络与上网、使用限制；
7. 明确品牌视觉按“品牌 + 设备类型”解析，不能用单一厂商图标暗示错误设备形态；
8. 将旧 M21 标记为已被本计划取代，保留其历史内容但不得继续作为执行依据；
9. 对难以逆转的“无长期双 UI”和“任务级事务”分别记录 ADR。

### 明确验收标准

- 仓库只有一份文档被标记为当前产品与领域基线；
- 全文检索不再同时存在两套“目标一级导航”；
- 当前基线不再要求保留经典页面一个发布窗口；
- `CONTEXT.md` 中 Device Profile 不包含分组成员关系，联网权限不再归属于限速能力；
- 当前基线明确区分 Unicode Device Alias 与 ASCII DHCP Hostname，任何中文备注都不会写入 dnsmasq hostname；
- 三个写入任务各自列出字段、事务范围和失败语义；
- 七个 P0 都有唯一的基线章节和可测试结论；
- 文档链接、Markdown 检查和术语检查通过；
- 本阶段不改生产行为，现有自动测试保持通过。

## 7. M22：五层覆盖矩阵与验收框架

### 目标

让每项产品承诺都能追到原型、后端、正式前端和实机证据，消除“原型完整等于产品完成”的误判。

### 任务树

1. 将现有 48 项能力拆分为稳定 Requirement ID；必要时按一个用户结果一行细分；
2. 补入新发现的需求：设备确认状态、图标偏好、独立联网权限、Router Context、期望/应用/效果三态、安装恢复、任务级事务、批量执行预算；
3. 为每行填写五层当前事实，未实现的内容诚实标记 `partial` 或 `not_started`；
4. 建立证据目录约定和机器可读索引；
5. 编写矩阵校验脚本，并接入本地验收命令；
6. 建立实机场景编号，至少包含：全部能力可用、无 floatip、无 eqos、两者均无、外部 DHCP、能力异常、续租前后、回滚失败；
7. 为后续里程碑建立“变更必须同步矩阵”的检查项。

### 明确验收标准

- 旧矩阵所有能力均有新 Requirement ID，数量核对无遗漏；
- 七个 P0 的正常和异常场景全部有独立需求行；
- 校验脚本能阻止重复 ID、缺少层级、无证据的 `verified` 和非法状态；
- 随机抽取 10 行均可从需求追到测试或明确阻塞原因；
- 当前生产缺失的图标持久化、DHCP authority、真实效果确认等不得标记为完成；
- 矩阵校验、现有 Go/Web 测试和前端类型检查通过。

## 8. M23：信息架构收口与一次性迁移契约

### 目标

在开发正式 UI 前冻结唯一导航、入口归属和无双写的一次性配置迁移方式。

### 任务树

1. 将每个旧入口的能力映射到设备详情、分组与计划、局域网设置或规则台账；
2. 更新低保真原型，只保留推荐方案作为正式目标，A/B/C 对照稿归档；
3. 设计幂等迁移器：读取现有 DHCP host/tag、eqos、firewall 和 floatip 配置，输出新模型计划；
4. 迁移前只读预览：已识别、冲突、无法识别、将保留原样和需要用户处理；
5. 迁移使用快照、版本和校验和；成功后新模型成为唯一写入源；
6. 定义旧页面、旧接口和旧 store 的删除清单，不建立双写层；
7. 将离线规则、孤立规则、批量删除和冲突定位保留到新的规则台账。

### 明确验收标准

- 所有旧页面能力都有且只有一个新入口；
- 迁移 fixture 覆盖静态地址、中文旧名称、DHCP 主机名、tag、旁路由、浮动网关、限速、断网和孤立规则；
- dry-run 零写入且逐条解释；重复执行迁移不新增配置、不改变结果；
- 冲突或未知项不会被静默丢弃，也不会阻断无冲突项的报告生成；
- 迁移失败时配置文件哈希恢复；成功后不再需要旧页面或双写；
- 原型只有一个正式推荐导航，规则台账不是一级入口。

## 9. M24：设备资料、品牌与图标闭环

### 目标

让用户备注、分类修正、品牌修正和图标偏好成为稳定、可解释、可恢复自动推荐的 Device Profile。

### 任务树

1. 扩展 Device Profile：Alias、Manual Category、Manual Brand、Icon Mode、Manual Icon Key；
2. 自动视觉解析顺序固定为：手动图标 → 品牌+类型视觉 → 类型图标 → 通用电脑；
3. 自动模式只持久化用户意图，不持久化可能过期的自动解析结果；
4. 支持恢复自动分类、恢复自动品牌和恢复自动图标，三者互不误删；
5. 建立稳定图标键、分类分组、资源尺寸和 fallback；
6. 至少提供 30 个原创或明确授权的用户自选图标，并保留生成来源、许可和人工审核记录；
7. ASUS 基准覆盖路由器与电脑两种类别，厂商文字与形态不互相替代；
8. 为 profile 文件设置版本、记录上限、原子写入和损坏降级；
9. 更新原型与后端契约测试，正式编辑 UI 留到 M30。

### 明确验收标准

- 未知设备默认电脑；修改类型后自动图标立即变化；
- ASUS + 网络设备得到 ASUS 网络设备视觉，ASUS + 电脑得到 ASUS 电脑视觉；
- 手动图标跨刷新和重启保持不变，分类更新不会覆盖；
- 恢复自动后重新跟随品牌+类型规则；
- 无效图标键、超长品牌、控制字符和损坏 profile 安全拒绝或降级；
- 30 个以上图标都具备稳定键、无障碍名称、分类和许可/生成记录；
- Profile 容量与文件大小有明确上限，压力测试不产生无界增长。

## 10. M25：能力拆分、安装与恢复闭环

### 目标

实现“缺什么，只锁什么”，并让安装、启用、异常恢复和返回原任务形成统一闭环。

### 任务树

1. 定义统一 Capability Interface，包含 `available`、`disabled`、`not_installed`、`error`、`unsupported` 及可执行动作；
2. 将 `internet_access` 与 `device_speed_limit` 完全拆分：前者依赖防火墙，后者依赖 eqos；
3. floatip、eqos、流量增强等能力通过同一读模型暴露，不由页面各自猜测；
4. 安装 Adapter 返回检查空间、软件源、安装中、成功、失败、版本不兼容和需要重试等结果；
5. 安装必须用户确认，不自动执行；技术包名只在确认或诊断中显示；
6. 定义草稿恢复 token：离开编辑器安装能力后返回原设备、原区域和未提交字段；
7. 保存前重新检查能力；修改了不可用字段则零写入，不相关字段可以在移除该修改后继续；
8. 已有配置依赖消失时保留 Desired Policy，Observed Effect 标记无法执行；
9. 测试无 floatip、无 eqos、能力 disabled、状态读取 error 和 unsupported。

### 明确验收标准

- 未安装 eqos 时仍可暂停和恢复设备上网；限速字段不可编辑且原因明确；
- 未安装 floatip 时其他路线、地址和联网权限可正常保存；
- 安装取消或失败不丢编辑草稿，不产生任何策略写入；
- 安装成功返回原任务，但不会替用户自动应用策略；
- 能力在编辑期间变化时，提交前预检阻止不安全写入；
- 依赖消失后原限速/浮动路线值仍可读，并显示“期望保留，当前无法执行”；
- Inventory、Profile 和不相关策略在任意能力错误时仍可使用；
- 测试设备分别验证 floatip 可用与 eqos 未安装场景。

## 11. M26：Router Context 与 DHCP 分配权

### 目标

让路线是否可编辑由后端权威结果决定，并诚实处理无法判断和多 DHCP 情况。

### 任务树

1. 将 Router Context 限定为“选定 LAN/bridge 的上下文”，不把全设备压缩成一个全局旁路由布尔值；
2. 归一拓扑位置、LAN 地址、上级网关、本机 DHCP 状态和判断证据；
3. DHCP authority 至少区分：`local`、`external_observed`、`none_detected`、`ambiguous`、`error`；
4. 输出 `routeEditability`、原因、可复制的本机网关地址和安全建议；
5. 本机未掌握 DHCP 时路线编辑只读，不提供“立即开启 DHCP”；
6. 多出口、多 LAN/VLAN、WAN 默认路由、静态默认路由和角色不明有明确降级；
7. 前端只消费 Router Context，不自行读取 UCI 或推断拓扑；
8. 原型覆盖主路由/旁路由 × 本机/外部/不明 DHCP 组合。

### 明确验收标准

- fixture 覆盖普通主路由、旁路由、本机 DHCP、外部 DHCP、无 DHCP、两个 DHCP 证据、多默认路由和读取失败；
- 只有 `local` 且能力健康时允许本机修改设备 DHCP 路线；
- `external_observed` 显示只读、主路由操作提示和本机地址复制；
- `ambiguous` 不误导用户开启 DHCP，也不伪装成可编辑；
- 角色确认只改变解释/推荐，不绕过 DHCP authority；
- Router Context 查询失败不影响设备列表和只读详情；
- 测试机当前拓扑结果与系统路由、DHCP 配置证据一致。

## 12. M27：上网路线的期望、应用与终端效果闭环

### 目标

不再把“服务器配置写入成功”误报为“终端正在使用该路线”。

### 任务树

1. 将状态拆为 Desired Policy、Applied Configuration、Observed Effect；
2. 定义诚实状态：未保存、应用中、服务器已应用、等待续租、已观察到新租约但终端效果无法验证、失败、恢复中、需要处理；
3. 明确 OpenWrt 无终端代理时不能可靠证明终端实际采用网关/DNS，禁止虚构 `active`；
4. 通过租约时间、host 映射和配置版本判断“续租发生”，但将其表达为“可能已更新/无法完全验证”；
5. 路线目标健康与设备是否实际使用路线分开；
6. 当前阶段固定“DNS 跟随路线”：路线编译同时生成匹配的网关与 DNS DHCP 选项，不增加第二个普通用户选择项；
7. 设备列表、详情、需要处理筛选和审计使用同一状态聚合；
8. 浮动网关显示虚拟 IP 当前持有者和健康，但不等同于终端路线已验证；
9. 支持续租前后、设备离线、随机 MAC 变化、租约源不可用和配置被外部修改。

### 明确验收标准

- 保存后首先显示“服务器已配置，等待设备更新”，不显示“已生效”；
- 观察到保存后的新租约时转换为“设备已重新获取地址，实际路线无法完全验证”或等价诚实文案；
- 没有观察证据时保持 pending/unverifiable，不随时间自动变为成功；
- 配置版本被外部修改时显示冲突并要求重新加载；
- 路线不可达、浮动网关降级和设备未续租是三个独立状态；
- 任一路线写入都使用同一目标生成网关与 DNS；测试不得出现网关已切换而 DNS 仍指向旧路线；
- 状态机表驱动测试覆盖所有合法转换并拒绝非法跳转；
- 重启后能够从持久配置和有限观察记录恢复正确状态，不把旧 pending 当成功。

## 13. M28：任务级事务、幂等与故障恢复

### 目标

用可实现的事务边界替代“整个设备抽屉绝对原子”的不现实承诺。

### 任务树

1. 为三个写入任务定义小而稳定的 Interface：Profile、Network、Restrictions；
2. 每个任务遵循 plan → validate → snapshot → apply → verify → rollback/recover；
3. Network 事务覆盖 DHCP host、地址、ASCII DHCP Hostname 和“网关 + DNS”路线；Unicode Device Alias 不进入该事务和 dnsmasq；
4. Restrictions 事务协调 firewall、eqos、计划、额度和单设备例外；
5. 跨文件/服务使用补偿事务，显式返回 `rolled_back` 或 `recovery_required`；
6. 幂等键使用持久状态版本或有界持久记录，不只依赖进程内 map；
7. 在每个写入和服务重载步骤注入失败，验证快照、回滚和恢复提示；
8. 建立启动恢复：发现未完成事务时先恢复或标记需要处理；
9. 审计记录计划摘要、结果和恢复状态，不记录敏感设备内容。

### 明确验收标准

- Profile、Network、Restrictions 三个 Interface 均有正常、无变化、冲突、验证失败、应用失败、验证失败、回滚失败和重复提交测试；
- Network 事务不会留下“地址已改、路线未改”的半配置；
- 中文 Device Alias 可保存且不改变 dnsmasq hostname；非法 DHCP Hostname 在写入前被拒绝并保持配置哈希不变；
- Restrictions 某个依赖不可用时在写入前失败，零修改其他配置；
- 进程在写入后、重载前和验证前中断，重启后均能恢复或明确进入 `recovery_required`；
- 同一幂等键和同一请求不重复写入；同一键不同请求返回冲突；
- 页面得到结构化阶段和恢复动作，不解析内部错误字符串；
- 删除旧的跨任务“大事务”承诺，正式文案与技术能力一致。

## 14. M29：分组批量执行、策略优先级与低资源优化

### 目标

让分组、计划和配额在大量设备上可预测、可批量执行、不会反复重载系统服务。

### 任务树

1. 冻结优先级：系统默认 → 全局策略 → 分组优先级 → 单设备例外 → 运行期约束；
2. 明确单设备允许联网是否能覆盖分组晚间暂停；按冻结基线实现而非依赖调用顺序；
3. 调度先计算全量差异，再生成按配置文件聚合的执行计划；
4. 同一批次中 DHCP、firewall、eqos 每个服务最多重载一次；
5. 用户新建了不可用能力规则时整次计划预检失败；已有规则在依赖消失时保留期望并报告降级；
6. 批次失败按 M28 恢复，逐设备输出结果但不留下不可解释混合状态；
7. 时区、夏令时、NTP 回拨/快进、跨午夜、重启和错过执行窗口有确定规则；
8. 调度队列、事件、成员、计划和重试均有上限；禁止每设备 goroutine/ticker；
9. 建立 20、256、2048 设备的 CPU、内存、写入次数和服务重载基准。

### 明确验收标准

- 同一输入无论设备迭代顺序如何，Effective Policy 完全一致；
- 256 台设备同一时刻切换计划时，每类配置只提交一次、每个相关服务最多重载一次；
- 任一预检失败时零写入；任一应用失败时结果为完全恢复或明确 `recovery_required`；
- 无 eqos 时暂停上网计划仍执行，限速计划显示能力不可用；
- 跨午夜、周日到周一、时区改变、NTP 回拨和重启测试通过；
- 100,000 次成员 churn 后所有 map、队列和事件保持在上限内；
- 256 MiB 限制环境不 OOM，稳态 RSS、CPU 和执行时长满足共同性能门。

6. 实现安装/启用/重试说明层及草稿恢复；

### 明确验收标准

- 安装返回后设备、区域和草稿不丢失；刷新或冲突时给出明确恢复选择；
- 正式 UI 不存在“经典列表”按钮，不存在两套相同任务入口；
- 三档尺寸无页面级横向滚动，键盘可完成全部主要任务，图标都有文字或无障碍名称；
- 前端类型检查、生产构建、组件测试和关键路径端到端测试通过。

## 16. M31：实机、约束环境、打包与发布门

### 目标

### 明确验收标准

- 配置迁移失败或写入中断时能恢复，且没有经典 UI 或双写作为隐性依赖；
- 重启后图标偏好、设备资料、Desired Policy、分组和恢复状态保持正确；
- 发布说明诚实列出 IPv6、终端路线效果验证、Bandix/eqos/floatip 和多 LAN/VLAN 的支持边界。
